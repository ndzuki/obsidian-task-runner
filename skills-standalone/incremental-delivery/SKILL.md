**Role**: Implementation Engine。你逐条执行**已批准**的计划，每条 AC 一个 tracer bullet，交付时带可独立复现的证据。

**分工**（别重复别漏）：

| 关注点 | 归谁 |
|---|---|
| 红绿重构的细节、好测试的定义、mock 边界示例 | `skill://tdd`（**主动调用型**，不进 agent 目录——所以下方自带一行版） |
| 逐条 AC 的推进节奏、写入即反馈、失败场景矩阵、阻塞证据、时间盒削 scope | 本 skill |
| 难缠 bug 的诊断循环（先建复现再假设） | `skill://diagnosing-bugs` |
| 测试是否值得保留（同义反复/实现耦合/缺覆盖） | `skill://test-quality` |
| 规范轴 + 需求轴的双轴评审 | `skill://code-review` |
| 一次性原型代码（跑完即弃） | `skill://prototype` |

**落点是 vault 的任务记录。** TASK 文件
（`<vault>/Projects/<项目>/Tasks/TASK-<id>-<slug>.md`）是交付记录的第一者。
**沿用既有章节名，不另造格式**——记录必须和历史上的 TASK 可比：

| 写什么 | 写到哪 |
|---|---|
| 每条 AC 的实现与命令证据 | `## 实现记录` → `### Round N · <日期>` |
| 失败场景矩阵结果（命令 × 预期 × 通过） | 同 `## 实现记录`（或独立 `### 失败场景` 子节） |
| 试错换方案的负向经验 | `## 踩坑记录` → `### <日期>: <现象一句话>` |
| 逐条 AC 的验收结论 | `## 验收记录` → `### Round N · <日期>` |
| 计划外变更、降级项（`~nice-to-have`） | `## 变更记录` |
| 分支 / PR / 合并状态 | frontmatter `pr_url` / `merge_status`；全部 AC 通过后置 `status: done` |

**没有 CLI 写回通道**（daemon 已停用）：frontmatter 直接编辑，但只动必要的键、保持既有
字段命名不变。**计划外的字段名不要发明**——那会让这份记录脱离历史序列。

## Pre-flight（开工前）

1. 计划已批准；若没有计划，先走 `skill://risk-aware-planning`。
2. 读 vault 的 `<vault>/Projects/<项目>/Notes/PROJECT-CONVENTIONS.md`（若存在）——它的规范与架构约束**优先级高于本 skill 和全局默认约定**。注释语言、代码风格、commit 语言、文档形态**逐条照办**，那不是偏好是项目规范。
3. 确认工作树状态：当前分支与计划约定的一致，工作区干净或已知脏点。**不要自建 worktree / 平行目录结构**——在既有 checkout 里干活（自建的工作树容易变成没人回收的孤儿目录）。
4. **最小变更**：只按计划实现 AC。不顺手重构、不格式化计划外的区域、不新增计划没有的抽象。已有仓库的认知负担优先。

## 先写决策，再写代码

计划里标了架构决策的，**在第一条 AC 之前**落成文档
（`<vault>/Projects/<项目>/Notes/adr/ADR-{id}-{slug}.md`），格式：

```markdown
# ADR-{id}: {title}

## Status
accepted

## Context
{为什么需要这个决策？有哪些约束和力量在拉扯？}

## Decision
{具体选了哪条路}

## Alternatives Considered
{评估过哪些替代方案，为什么否掉}

## Consequences
{什么变容易了？什么变难了？风险在哪}
```

**决策和依赖它的代码放进同一个 commit。** 决策是蓝图，不是脚注。

## Prototype Gate（高风险 Step 的前置验证）

计划里 `risk: high` 的 Step 带了「Prototype 建议」（PASS/FAIL 条件）时，**在实现该 Step 之前**先跑原型：

1. 读计划的 Prototype 建议，取出 PASS / FAIL 条件。
2. 走 `skill://prototype` 写**一次性**原型代码（不入主分支、不留测试）。
3. 严格按条件判定结果：
   - **PASS** → 进入该 Step 的 Tracer Bullet，在实现记录里标 `✅ 原型已验证`。
   - **FAIL** → **不进入实现**。带原型证据找用户：原型代码路径、运行输出、违反了哪条 FAIL 条件、建议的替代方案。

这样追问就从"你觉得该怎么设计？"变成"原型验证了 X 不可行（证据在此），建议 Y，你同意吗？"——**一轮定案，而不是多轮猜测**。

> **例外：验证器是持久资产。** 若这个原型同时是**其它工作的验收标准**（比如一段可复用的冒烟脚本或门禁），它就不是一次性的——必须提交进主分支，并以主分支版本为唯一权威。教训：验证器留在未提交的工作树里，接手的人找不到，工作树一重建就永久丢失。

## Tracer Bullet（逐 AC 推进）

每条 AC 独立走一遍红-绿-重构。**一行版**（细节归 `skill://tdd`）：**先写一个失败的测试并确认它因正确的断言而失败**（不是编译错、不是 panic）→ 写**刚好够**让它通过的代码（不做 DRY、不提前抽象）→ 全绿之后才重构。绝不先批量写完所有测试再写代码——那是在测试"想象中的行为"。

1. **测试打在计划声明的 Seam**。计划没写 Seam 行时，取该 Step 的**最高公共接口**（最接近调用方可观察的层）。
2. 记录实现与测试证据。
3. 每条 AC 完成后**重新读一遍计划**，确认下一条 AC 的前置仍然成立。

**计划外 Seam = 架构信号**：某行为无法通过计划声明的 seam 测试（必须测内部、必须新增 mock 边界、或 seam 本身放错层）→ 不要静默绕过，也不要换层硬测。这是个信号：Step 边界或接口设计需要修正 → 回到 `skill://risk-aware-planning`（或 `skill://design-pass`），附证据（"想测什么、为什么测不到"）。

### 写入即反馈

每条 AC 的 Green 落地后**立刻**跑受影响包的测试与静态检查（Go: `go vet ./...` + `go test -race ./<受影响包>`），不要等全部 AC 完成再一次性跑。

理由很实在：错误在产生时暴露，修复成本是分钟级；攒到会话尾部再集中修，就变成"失败重派 + 审计打回"的主要来源。**全量测试留到完成检查。**

## 失败场景矩阵（强制，返工的头号来源）

实现 AC 时**只验证主成功路径 = 未完成**。"测试全绿、生产爆炸"几乎全部来自只测了 happy path。每条**存在可失败路径**的 AC，按矩阵逐项补负向测试（按相关类别取，不必全做）：

| 类别 | 要构造什么 |
|---|---|
| 权限/认证 | 401/403、无权限调用、token 失效 |
| 并发/排队/竞态 | 信号量耗尽、槽位释放、冲突写回、重试预算耗尽。**用 `-count=3`（或更多）重跑**——单次通过不算证据；flaky 必须抓到根因修，不许"重试到绿"掩盖 |
| 吊销/删除/幂等 | 删除后重放、幂等拒绝（409）、已成功重复提交 |
| 非法输入 | 校验失败、空值、超长、重复 |
| 序列化/契约形状 | `null` vs `[]`、字段缺失、时间戳与枚举边界 |
| 跨引擎方言 | dev 用 SQLite 而 test/prod 用 MySQL 时，存储与迁移**必须在 prod 引擎实测**（严格模式、零日期、TEXT 默认值、字符集） |
| 失败被容错掩盖 | 代码对错误"打印后继续"产生假成功——失败要 fail-fast，测试要锁住这个行为 |
| **恢复路径**（状态机/重试类） | 每个可失败点补一条"失败后修正输入重跑"的验证，确认恢复不被旧失败状态污染。**只测失败本身、不测恢复 = 覆盖不完整** |
| 生命周期/复用 | 同标识重跑产生新内容、旧失败条目残留、长生命周期复用（事件/TTL 过期） |

两条纪律：

1. **测试要驱动真实实现** — 优先 httptest / 真实依赖 / 内存版真实组件，不只靠 mock。mock 发现不了"远程调用多了一次""参数没传对"这类问题。
2. **失败信息要可断言** — 错误串稳定（如 `digest mismatch after push ...`），测试锁住这些串；按子串分类（permanent/retryable）的逻辑尤其如此。

每个失败场景在交付记录里标注：命令 + 预期 + 通过输出。

## 排障先看决策，不猜

遇到"看似没生效 / 没处理 / 像环境问题"的异常，**第一步开到 debug/verbose 看真实决策**，再下结论。禁止靠 info 日志的启动行猜。

- 把日志级别调到 debug（如 `LOG_LEVEL=debug`），grep **决策行**（decision made / action=X / sync succeeded version=N），而不是只看启动信息判断"有没有干活"。
- 很多"卡住"其实是正常的 Noop（空配置等待下一轮）。先确认是 Noop 还是真卡住，再动手。

## 阻塞必须附根因证据

转阻塞或找用户之前，**必须附根因证据**：至少一条可复现的日志/命令输出 + 一句根因判断（debug 日志片段、复现命令输出、代码路径）。

- 禁止把"疑似环境问题 / 看起来没处理"当阻塞理由绕开——这是最常见的绕过排查的陷阱。
- 根因确实不明时，如实写"根因未明 + 已排除 X/Y"，**不要归咎环境**。
- 需要用户决策时走 `skill://grilling`，把证据摆前面："复现命令 + 输出 + 我判断的根因 + 建议方案"。

**上游事实类失败不要重试循环**：门禁不通过（上游 PR 未合入、依赖未就绪、环境不可用）是**上游事实问题**，不是需求或计划问题。重复重出计划不改变任何上游事实，只烧 token。写清证据、标记阻塞、把决定权交回用户。

> 反面教训：一个门禁失败的任务在同一份需求上被 replan 了 17 轮，零收敛，每轮都是一次最高推理强度的实现会话。

## Scope Hammering（时间盒过半自动削 scope）

若用户或需求给了时间盒（如 small=30m / medium=2h / large=6h），**过半时**做一次：

1. 评估剩余 AC 的核心程度：是 must-have 吗？能降级吗？
2. 非核心 AC 显式标为 `~nice-to-have`，**写进交付记录通知用户**（不许静默丢）。
3. 优先交付核心 AC。降级项不阻塞交付，后续可作为新需求追加。

判断标准（Shape Up Ch.14）：

- 没有这个功能，用户能否完成核心任务？（能 → nice-to-have）
- 这是新问题，还是已有 workaround 的老问题？（老问题 → nice-to-have）
- 这个情况发生的概率？（<5% → nice-to-have）

## 踩坑记录

**只要过程中出现"以为方案 X 对 → 失败 → 换 Y 才成功"，就追加一条**：

```markdown
### {YYYY-MM-DD}: {现象一句话}
- 现象: {观察到的失败行为}
- 失败方案: {试过但不成立的方案与失败证据}
- 根因: {失败原因分析}
- 成功方案: {最终生效的方案}
- 相关文档: {引用的文档路径，可选}
```

成功方案可以另写成决策文档；**踩坑记录专记失败路径**——决策文档里不写"试过 X 不行"。零试错的，显式声明"无踩坑"，别留下"是忘了写还是真没有"的歧义。

## 完成检查

1. 全部 AC 有**独立可复现**的证据（命令 + 预期 + 输出），不是"已实现"三个字。
2. 失败场景校验：可失败路径都有负向测试，并发/竞态类 `-count=3+` 通过，跨引擎项目有 prod 引擎实测证据。缺失即不通过。
3. 踩坑记录已写或有显式"无踩坑"声明。
4. 计划里引用的知识/文档，逐条确认已应用或说明为何不适用。
5. 每个 `risk: high` Step 有原型证据（PASS 记录或 FAIL + 结论）。
6. 跑全量测试（Go: `go test -race ./...`）。
7. 跑 lint。
8. 测试质量自查（细节归 `skill://test-quality`）：**同义反复**（期望值从被测代码反推，`assert.Equal(t, f(x), f(x))`）、**实现耦合**（mock 内部协作者、测私有方法）、**缺边界覆盖**（新公共 API 没有对应的失败/边界用例）。三类里命中 critical 的必须修完。
9. 变更自查（细节归 `skill://code-review`）：**规范轴**——是否符合本项目规范（读 vault 的 `Notes/PROJECT-CONVENTIONS.md` 或抽样既有代码）、有无 code smell；**需求轴**——实现与 AC 是否一一对应、有没有计划外的 scope creep。

## 交付摘要

收尾产出一段**给人看**的摘要：写进 TASK 的 `## 验收记录`（vault），并直接回复给用户。

```text
{改了 N 个文件，+A/-D 行，M 个测试通过}
test-quality: 🔴0/🟡0/🟢N | code-review: 规范轴 N / 需求轴 N
时间盒: {small|medium|large} | 降级: {N} 条 ~nice-to-have
对比: 实现前用户怎么做，实现后改善了什么（一句话）
风险自评: low/medium/high
未覆盖/存疑: {显式列出，不藏}
```

**Diffstat 与测试结果给事实，风险自评给判断，存疑项给诚实。** 这三样齐了，用户才能在三十秒内决定要不要继续。
