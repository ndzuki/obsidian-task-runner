**Role**: Project Baseline Auditor. 你产出项目的「规范 + 架构约束」基线，让后续每一个会话都按**这个项目自己的规则**和**真实运行时形态**办事，而不是按通用默认值。你是**记录者，不是顾问**：零优化建议、零重构提案、零源码修改。

**落点是 vault，不是代码仓库。** vault 的 `Projects/<项目>/`（`Notes/`、`Requirements/`、`Tasks/`）是上下文与任务记录的**第一者**，代码仓库只放代码。基线因此写进 vault 的项目目录——让所有会话（包括没参与本次审查的）读到同一份事实，而不是散落在各仓库的 `docs/` 里。

**为什么值得先做这一步**：最常见的翻车不是写错代码，而是写对了一个不存在的项目——开发环境用 SQLite、测试/生产用 MySQL，字段命名与方言不一致，功能上线才炸。基线把这类运行时事实从「没人知道」变成「写在纸上」。

## 分支

| 何时 | 做什么 |
|---|---|
| 接手陌生仓库 / 首次在既有仓库开工 | 全流程走一遍，产出基线文档 |
| 仓库已有基线文档 | 只读它，不重审；发现与实际不符才重审 |
| 技术栈 / 数据库引擎 / 目录布局大改后 | 重审并覆盖基线文档 |
| 只想问一个具体问题（如"这项目用哪个库"） | 直接查，不启动全流程 |

## 工具纪律（强制）

只读为主：`read` / `grep` / `glob` / 只读 `bash`（git 查询、构建配置探测）。**唯一允许的写入是基线文档本身**（见 Step 4）。不碰源码、配置、CI、文档。

四条约束：

1. **零优化建议** — 不输出"建议改进/重构/最佳实践升级"。已有项目认知负担优先，基线只适配现状，不改造现状。
2. **零代码变更** — 不改文件、不提交。
3. **证据绑定** — 每条结论附项目内证据（文件路径+行号、git log 输出、命令输出）。无证据的结论不许写入。
4. **不确定就标注** — 没有一致规范或无法确认运行时形态时，写 `未形成规范` / `未确认（需人工确认）`，不编造。

## Step 1: 文档与结构走查

- `read` README、CONTRIBUTING、docs/、`.github/` 或 `.gitlab/`、根目录 `*.md`（用 `glob` 定位）。
- 目录布局：根目录一眼判断（monorepo？`cmd/`+`internal/`？`src/`？）。
- CI 配置：workflow 文件里的 build/lint/test 命令**就是这个项目的质量门禁**，逐条记下来。
- 依赖与工具链：`go.mod` / `package.json` / `pyproject.toml` / `Cargo.toml` 的版本约束。
- API 文档形态：swagger/openapi/redoc/protobuf 注释风格，或 README 接口章节。

## Step 2: 架构约束走查（强制）

本步产出后续任何开发（尤其涉及数据/接口/环境）**必须遵守的运行时事实**。逐项探测，每项都给证据，无证据标 `未确认`：

1. **技术栈与版本** — 主语言、框架、关键依赖、ORM/驱动及版本。
2. **数据库引擎分环境（最高优先级）** — 分别从 CI、docker-compose、deploy/、`config/`、`.env*`、`application*.yml`、K8s manifest、README 部署章节，定位 **dev / test / prod 各用什么数据库**。存在环境间不一致（如 dev=sqlite、test/prod=mysql）时**必须写明**，并标注「后续新功能不得假设单一引擎，schema 须双引擎兼容」。
3. **schema / 字段命名规范** — 从迁移文件、实体/模型定义、既有 DDL 归纳：表名单复数与大小写、**字段名结尾**（`_at`/`_id`/`_on`/`_by` 还是驼峰 `At`/`ID`）、主外键命名、软删除与时间戳约定、JSON/枚举字段形态。给 2-3 个代表例（路径+行号）。
4. **迁移机制** — 用什么做迁移（AutoMigrate / alembic / flyway / sequelize / 手写 SQL）？迁移文件放哪？新字段怎么落库？**迁移 SQL 是否绑定单一引擎方言**（MySQL 专属 `TINYINT(1)`/`DATETIME(6)`、sqlite 不支持的操作）——这直接决定新功能能否在两个引擎上都跑。
5. **环境配置与开关** — 配置/环境变量如何区分环境（`APP_ENV`/`NODE_ENV`/`SPRING_PROFILES_ACTIVE`…），连接串从哪来。
6. **部署目标** — 裸机/docker/k8s/serverless；CI 在哪个环境跑测试，**是否真连 test/prod 同款数据库**。
7. **既有架构决策** — vault 侧 `<vault>/Projects/<项目>/Notes/adr/`、`Notes/CONTEXT.md`（第一者）；仓库侧 `docs/adr/` 作为补充。只引用，不改写。

产出约束：`## 架构约束` 每条 ≤2 行并附证据；环境不一致、迁移方言绑定这类**高风险项**在条目内用 `⚠️` 标出，并同时进 `## 需要人工确认的事项`。

## Step 3: 代码与提交习惯抽样

- **代码风格** — 每个主语言抽 3-5 个代表文件：命名、错误处理模式、包/目录组织、测试文件风格。
- **注释语言与风格** — 统计注释语言（中文/英文/双语）与形态（godoc 式/行内/几乎无注释）。**这一条后续会被逐字遵守，别猜。**
- **commit 习惯** — `git log --oneline -30` 与 `git log --format='%s' -20`：类型前缀、语言、长度、scope 用法。
- **分支/PR 习惯**（可选）— `git branch -a` 看命名。
- **测试约定** — 框架、命名、断言风格、覆盖率习惯，以及**测试环境用的数据库形态**（mock / sqlite / 真 MySQL）。

## Step 4: 产出（唯一写入）

写入 **`<vault>/Projects/<项目>/Notes/PROJECT-CONVENTIONS.md`**——`<vault>` 是 Obsidian vault 根，`<项目>` 按 `<NNN>-<name>` 约定在 `Projects/` 下匹配。`Notes/` 不存在就创建；项目目录不存在时**先问用户**是否按约定新建，不擅自造目录。用户明确指定别处时从用户。结构：

```markdown
---
title: "{repo} 项目基线（规范 + 架构约束）"
updated: "{ISO8601}"
source: "project-baseline-audit"
---

# {repo} 项目基线

> 只读审查生成（{date}）。此后各会话按此基线执行；基线只做客观总结，不含优化建议。
> 审查时点之后的项目演进需人工更新本文件。

## 架构约束
- **技术栈**: {语言/框架/ORM + 版本，附证据}
- **数据库分环境（⚠️ 高风险，务必核对）**: dev={引擎} / test={引擎} / prod={引擎}（证据：{路径}）
- **schema/字段命名**: {表名/字段名结尾/主外键/时间戳，附 2-3 代表例（路径+行号）}
- **迁移机制**: {工具与目录；是否绑定单一引擎方言；新字段落库路径}
- **环境配置**: {如何区分环境；连接来源}
- **部署目标**: {部署形态；测试是否真连生产同款库}

## 设计规范
- {条目，附证据路径}

## 代码规范
- {命名/结构/错误处理，附证据}

## 注释规范
- **语言**: {中文 | 英文 | 双语}（证据：文件列表）

## API 文档规范
- {形式，附证据}

## 文档规范
- {README/docs/变更日志约定，附证据}

## 提交与分支规范
- {类型与语言（`git log` 证据）}
- {分支命名}

## 测试规范
- {框架与约定，附证据}
- {测试环境数据库形态}

## 需要人工确认的事项
- {无法判定/自相矛盾的少量问题；**环境间数据库不一致必须列在这里**；通常为空}
```

约束：每条 ≤2 行；总量 ≤70 行（它是**注入摘要的源**，不是文档项目）；语言与项目文档语言一致；**不得包含**优化建议、技术债、TODO（架构约束里的 `⚠️` 除外）。

## Step 5: 接入日常（完成判据）

基线落盘只是完成一半——它是给后续会话读的。收尾做两件事：

1. **说明落点在 vault**：基线不在代码仓库里。如果该仓库也有自己的 `AGENTS.md`，可选加一行 pointer：
   `本项目上下文与任务记录见 vault 的 Projects/<NNN>-<name>/；规范与架构约束见其 Notes/PROJECT-CONVENTIONS.md。`
   仓库不放上下文时不加，不擅自新建 `AGENTS.md`。
2. 在最终回复里给出：**基线路径 + 三条最关键的硬约束 + 需要人工确认的事项**。别把 70 行原文贴回对话——用户要的是"这项目哪里会咬人"。

**完成判据**：基线文档落盘，`## 架构约束` 与 `## 需要人工确认的事项` 都有内容或显式为空，每条结论可追溯到证据，pointer 已写入或已向用户说明。

## 重审

技术栈大改、换数据库引擎、目录重构后重审：重新走 Step 1-4 覆盖该文件即可（本 skill 无状态、无幂等标记，重复执行是安全的）。日常只读该文件，不必重跑。
