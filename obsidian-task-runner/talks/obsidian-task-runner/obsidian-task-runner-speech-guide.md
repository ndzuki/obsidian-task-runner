# Obsidian Task Runner 演讲指南

> 面向组织内混合听众（技术 + 非技术）的推广演讲策略、节奏和注意事项。

---

## 一、听众分析

### 典型听众画像

| 角色 | 关心什么 | 不关心什么 |
|------|---------|-----------|
| PM / PO | 需求可追溯、交付可预期、减少沟通成本 | Go 编译、systemd、fsnotify |
| Tech Lead | 代码质量、安全边界、团队采用成本 | Obsidian 插件细节 |
| 开发工程师 | 省多少时间、和现有工具链的集成、可控性 | PPT 级别的流程描述 |
| 设计师 / 运营 | "这东西能帮我做什么？我需要学什么？" | 任何技术细节 |
| 管理层 | ROI、风险、推广难度 | 实现方案 |

## 二、非技术听众的核心问题："我能用它干什么？"

### 关键洞察

非技术听众（PM、运营、设计师、管理者）不会问"怎么实现的"——
他们只关心一个问题：**"我不用写代码，这东西对我有什么用？"**

如果只讲功能和技术架构，他们会礼貌地听完，然后觉得"这是开发的事"。

**必须让他们"看见自己"**——用一个完整的角色故事，展示他们的一天如何改变。

### 推荐案例：PM 小林的一天

> 完整案例文档：[`obsidian-task-runner-nontech-case.md`](obsidian-task-runner-nontech-case.md)

**案例结构**（演讲中用 5 分钟讲）：

1. **场景一（1.5 分钟）**："过去 — 一个导出功能的 72 小时"
   - 时间线展示 PM → Dev 反复沟通的完整链条
   - 让听众感受"72 小时里真正的创造不到 10 分钟"

2. **场景二（2 分钟）**："现在 — 同一个需求，4 小时"
   - 时间线对比，强调两个数字的巨大反差
   - 每个 Gate 处用钥匙图标 🔑 强化"你掌握控制权"

3. **扩展（1 分钟）**："小林还能做什么"
   - 探索性提问（"如果加 PDF 导出会怎样？"→ 30 分钟拿到技术评估）
   - 小修小补（文案改动 → 半小时上线）
   - 数据需求（"每周发邮件汇总新增用户" → AI 出方案）

4. **收尾（0.5 分钟）**："需求文档就是沟通媒介"
   - PM 不需要学会写代码，PM 只需要学会写好需求
   - AI 读得懂，AI 出方案，AI 实现——PM 只判断"是不是我想要的"

### 不同角色的一句话价值

在讲完案例后快速过一遍，让每种角色立刻对号入座：

| 角色 | 一句话 |
|------|--------|
| PM | "写完需求 30 分钟看到技术方案，不用排队等开发给你评估" |
| 运营 | "'帮我加个数据看板' → 下午就能用" |
| 设计师 | "文案调整、颜色修改——自己搞定，别等前端排期" |
| QA | "写好复现步骤，AI 帮你修 bug 并跑回归测试" |
| Tech Lead | "把重复性 CRUD 外包给 AI，团队聚焦架构和复杂业务" |
| CTO / 管理者 | "每行代码有记录、每个决策有依据、新人接手不需要翻三个月聊天记录" |

## 三、演讲策略：三层洋葱模型
### Layer 1 — 共情层（所有人）
**3 分钟** — 用一个真实痛点开场，建立"我们都遇到过这个问题"的共鸣。

> "上周五下午 5 点，产品丢过来一个需求——'加个导出 CSV 的功能，周一要'。你打开 IDE，建分支，写 API，写测试，跑 lint，提 PR，等 review……这些步骤里，有多少是真正的'创造性工作'？"

然后用一句话定位 OTR：

> "Obsidian Task Runner 做的事情很简单：你在 Obsidian 写好需求，它在后台自动检查需求成熟度、出计划、写代码、跑测试，最后把 PR 放在你面前——整个过程你只需要确认三次。"

### Layer 2 — 信任层（非技术听众重点）
**5 分钟** — 建立对"AI 自动写代码"这件事的信任。这是非技术听众最大的心理障碍。

**核心信息**：三个 Gate，三个开关。

```
plan_approved: true   →  "我确认了计划，你可以写代码了"
merge_approved: true  →  "我 review 过了，你可以合并了"
**技术要点**（演讲中无需展开，备 Q&A 用）：

- **成熟度自动分级（Refining）**：daemon 先 headless 检查需求文档是否完备。完备的直接出计划；不完备的按三分类收敛——事实类自动修正、有明确建议的低风险项自动采纳（留 `auto_accepted` 审计，可推翻重跑），只有真争议才弹 Grilling 交互。避免成熟需求反复打断用户。
- **同一 TASK 只有一个 Grilling 会话入口**：不是“全局只能 grilling 一个任务”。`grill_owner` 防止同一任务被两个 agent 同时追问；daemon 跨全部 Kitty 窗口按 task ID 检查 tab/window title，并用 per-task flock + debounce 防止重复扫描或重启再次开 tab。不同任务仍可各自拥有独立 Grilling tab。
- **阶段 Skill 按需加载**：出计划、写代码、合并各自独立 Skill，每次只加载 ~185 行指令（原 827 行单体的 22%），降低 token 消耗。
- 新项目永远停在 Round 1 等确认，绝不会自动创建
- 需求变更后重新出计划，再次停在 plan-review，不会跳过
- `auto_approve=true` 的完全自主任务（无 ADR 提议）首规划自动批准跳过 Plan Review——声明式信任，ADR 提议时强制人工（备 Q&A）

### Layer 3 — 落地层（技术听众重点）
**7 分钟** — Demo + 架构。技术听众最关心"这玩意到底怎么跑起来的、我能信吗"。

**新增亮点**：Grilling 对齐——AI 在出计划前自动追问模糊点，通过 Kitty 终端新 tab 弹出，一次一问，带推荐答案。`needs-grilling` 是暂停状态；`grill_owner` 解决“谁拥有这次对话”，Kitty tab 去重解决“入口只能有一个”，两者不是同一层。Daemon 按 task ID 跨 Kitty 窗口识别已有 tab，标题变化、Unicode JSON 转义、重复扫描和 daemon 重启都不会产生第二个入口；无法可靠解析 Kitty 状态时 fail closed，不创建 tab，保留桌面通知 fallback，后续扫描重试。用户完成后 requirement-elaborator 自动恢复；Round 2 遇到阻塞同样会暂停并通知用户。**重复争议自动收敛（v0.23+）**：同一问题问过两轮无人回答，不再逐任务重复弹窗——争议并入项目级 `Grilling-Decisions.md` 清单，多个任务共享同一需求时问题自动去重合并，用户一次性回答，PM 统筹自动分发写回各需求，任务各自回 refining 复验。

## 五、Demo 设计（最重要的一环）

Demo 是整场演讲的核心。建议采用 **"录制 + 现场解说"** 的方式（避免现场网络/模型延迟翻车），但保留一个**现场手写需求**的环节以证明真实性。

### Demo 流程

1. **打开 Obsidian**，展示 Vault 结构和 Tasks-Dashboard 看板（10 秒）
2. **现场写一个简单需求**：`REQ-demo-export-csv.md`
   - 内容：给某个 API 加 CSV 导出，3 行描述 + 2 条完成标准
   - 目的：证明"写需求很简单"
3. **保存** → 展示 daemon 自动创建 TASK（切到终端看 `otg daemon --once` 输出）
4. **切回 Obsidian**，打开生成的 TASK，填写 `assignee: deepseek`，保存
5. **讲解三个 Gate**，展示 `plan_approved: true` 的填写位置
6. **播放录制**（或现场跑）：Round 1 出计划 → 展示任务文档中的实现计划
7. **播放录制**：Round 2 实现 → 展示 git log、代码 diff
8. **回到 Obsidian**：展示任务文档的完整记录（计划、实现、验收）
9. **切到 Dashboard**（高潮收尾）：
   - ADR 提议待审 query：展示 AI 提议的架构决策排队等批准
   - 架构决策记录 query：展示已累积的 ADR 目录
   - 收尾句："这不是 PPT——是真实在跑的系统。"
10. **展示 CONTEXT.md**：项目共享词汇 + Patterns + Anti-patterns
- 提前录制好完整流程的 screencast（2 分钟快放）
- 现场只做"写需求 + 看结果"两个互动环节
- 在播放录制时暂停讲解关键节点

## 六、演讲技巧

### 语言策略

| 场景 | 说法 |
|------|------|
| 介绍功能 | "你在 Obsidian 写需求，它自动实现代码" |
| ~~不要~~ | "fsnotify 监听目录变化后触发 daemon 调度 OMP agent" |
| 介绍安全 | "没有你的确认，它不会 push 一行代码" |
| ~~不要~~ | "merge_approved 字段控制 Merge Phase 的 yolo 权限" |
| 介绍价值 | "把重复劳动交给 AI，把决策留给自己" |
| ~~不要~~ | "通过三轮状态机实现 human-in-the-loop 的渐进式交付" |

### 处理质疑的预判回答

**Q: AI 写的代码质量能信吗？**
> "这正是三个 Gate 存在的原因。Round 1 你审计划——方向不对就改需求。Round 2 后你 review 代码——和我们平时 code review 一样。而且它强制跑测试和 lint，不通过不会进 review。另外它会自动维护 CONTEXT.md 和知识库，下次类似任务会更准确。"

**Q: 会不会偷偷 push 代码？**
> "不会。Round 1 和 Round 2 完全在本地操作——建分支、写代码、commit。只有你在 merge_approved 填 true 之后，Merge Phase 才会 push。代码里这是显式检查的，不是靠 prompt 约束。"

**Q: 和 Cursor / Copilot 有什么区别？**
> "互补关系。Cursor/Copilot 是编码助手——帮你写一行或一个函数。OTR 是流程自动化——从需求到 PR 的全链路。你可以在 OTR 生成的分支上继续用 Cursor 改代码，不冲突。"
**Q: Grilling 是什么？为什么要 AI 追问我？**
> "Grilling 是 AI 在出计划之前和你的一次对齐对话——一次一个问题，每个问题都带推荐答案。为什么要这样？因为'加个审批功能'这句话太模糊了——几级审批？超时自动驳回还是人工催？驳回回退到哪一步？这些模糊点如果 AI 自己猜，很可能猜错。Grilling 用 5-10 个问题把模糊点全部消除，后面的计划和代码才精准。你在终端里会看到一个新 tab 弹出来——切过去对话就行。"

**Q: 为什么不会不停弹出 Grilling tab？多个任务能同时 Grilling 吗？**
> “去重粒度是 TASK，不是全局。`grill_owner` 防止同一个任务被两个 agent 同时追问，daemon 还会跨所有 Kitty 窗口按任务 ID 查找已有 tab；并发扫描和重启再由文件锁与 debounce 兜底。所以 TASK-066 只会有一个入口，但 TASK-066 和 TASK-068 可以各自有一个 tab、互不阻塞。如果 Kitty 状态看不清，系统宁可不新开，改用桌面提醒，下一轮再重试。”

**Q: AI 写代码写到一半卡住了怎么办？**
> "这是设计内的。AI 遇到自己解决不了的问题——比如测试连续 4 次失败、发现计划里没覆盖的设计决策、依赖冲突——会自动暂停，在你的终端弹出新 tab，把卡住的原因和需要你决策的问题写清楚。你解决了，它从原地继续。不会卡死，不会假装没问题继续写错误的代码。"
**Q: 安全吗？数据会泄露吗？**
> "代码全程在本地。只有 Merge Phase 走 git push 到你的仓库。OMP agent 调用的模型取决于你的配置——可以用私有部署的模型。"

**Q: 安装复杂吗？**
> "一条命令：`otg install --vault <路径>`。剩余是 systemd 自动管理。"
