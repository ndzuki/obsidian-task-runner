## Slide 4: OTR 是什么

【翻页。】

这就是 Obsidian Task Runner 做的事情。

左边——你在 Obsidian 写需求。中间——AI 先和你对齐对话消除模糊点，然后出方案、写代码、跑测试。右边——代码变成 PR，放在你面前。

整个过程你只需要三件事——【指向屏幕】——一次对话确认方向，确认计划，确认合并。

---

## Slide 5: 完整流程

【翻页。】

看这个流程。从写需求开始——

AI 自动创建任务 → Round 1 出实现计划 →【指向菱形】这里停一下，等你确认——

你确认了 → Round 2 写代码 →【指向第二个菱形】这里又停一下，等你 review——

你确认了 → push、PR、合并。完成。

【停顿。】

只有两个菱形。两个需要你按"确认"的地方。其他地方——全部自动。

## Slide 6: 三个 Gate

【翻页。】

Grilling 对齐——我们叫它 Gate 0。AI 读到你的需求，发现有模糊点——“加个审批功能”——几级审批？超时怎么办？驳回回退到哪？AI 不会自己猜。而且它先自己消化一遍：查得到的事实自己修正（比如引用了不存在的 ADR 编号），有明确建议且低风险的问题直接采纳并留审计标记——只有真正影响边界的争议才来问你。这里有两层防重：`grill_owner` 保证同一个任务只有一个人或 agent 在追问；daemon 再跨所有 Kitty 窗口按任务 ID 检查 tab，保证只开一个对话入口。即使重复扫描、daemon 重启、任务标题变化，也不会再弹第二个 tab。然后 AI 一次问一个问题，每个问题带推荐答案。5–10 个问题把模糊点消除，才进入 Planning。如果同一个问题问了两轮你都没答，它不再重复弹窗——把争议汇总到项目级决策清单，攒一批你一次性回答，答案自动分发回各个需求。如果会话超时，默认 30 分钟自动释放所有权，不会永久卡住。

第一个 Gate：plan_approved。AI 出完计划之后，等你审。方向对不对？步骤合不合理？如果有架构决策——比如选事件溯源还是 CRUD——AI 会在 ADR 提议里写清楚，等你一起审。你觉得 OK，改个 true，保存——AI 才开始写代码。这个 Gate 可以按任务声明跳过：标注了 auto_approve 的完全自主任务（没有架构决策的那种）首轮计划自动通过——声明式信任，随时可关。

第二个 Gate：merge_approved。AI 写完代码、跑完测试和 lint 之后，等你 review。你觉得 OK，改个 true，保存——AI 才去 push 和合并。

【停顿。】

就像你带一个实习生——先聊清楚要做什么，再看方案，觉得靠谱才让动手。写完了你还得 review，才让合并。

区别是什么？这个"实习生"——主动追问消除误解、不会累、不会漏、每一步都自动留记录。

【翻页。】

所以你的角色变了。

过去——你是执行者。设计方案、写代码、提 PR、等 review——从头跑到尾。AI 最多帮你写几行代码。

现在——AI 是执行者。出方案、写代码、写测试、跑 lint、提 PR——AI 从头跑到尾。

你做什么？【指向两个确认点】你只做 AI 做不了的事——判断方向，审查质量。

## Slide 8: 安全边界

【翻页。】

有人可能会想——"AI 会不会偷偷把代码推上去？"

不会。这是显式检查，不是靠 prompt 约束。

Round 1 和 Round 2——只在本地操作。建分支、写代码、commit。不 push，不建 PR，不 merge。

Merge Phase——只有你在 merge_approved 填了 true 之后，才会执行 push、建 PR、合并。

【指向屏幕上的红线。】

这条线以上——AI 自由行动，但出不了你的机器。这条线以下——需要你的明确授权。

额外保障：新项目永远停在 Round 1，你不确认不创建文件。需求变更后重新出计划，再次停在 plan-review，不会跳过。

## Slide 10: 全流程可追溯

【翻页，跳过 Slide 9（30 分钟版才用）。】

还有一个好处——每一步都有记录。

一个 TASK 文件里面：实现计划——版本化的，每次出方案不覆盖旧的。实现记录——每步做了什么。验收记录——测试过没过、lint 过没过。执行摘要——完整时间线。变更记录——审计追踪。

【停顿。】

三个月后你回看这个需求——不需要翻 git log 猜"当初为什么这么做"。答案全在这个文件里。

## Slide 11: 项目知识

【翻页。】

而且——每个项目自动积累知识。

【指向 CONTEXT.md。】

首先是共享词汇表——"Order"就是"Order"，不会有人写成"Purchase"或"Transaction"。AI 和人用同一套语言讨论项目，沟通成本降了，代码命名也一致了。

现在还多了一层——daemon 在调度 OMP 时，会从 CONTEXT.md 提取约束、领域术语和 ADR 摘要，直接注入到 prompt 头部。agent 第一屏就能看到项目边界，不用再花时间读文件和理解上下文。

效果是什么？第一个任务的时候，AI 花 20 分钟读代码理解项目。第十个任务的时候，CONTEXT.md 已经积累了足够的知识——agent 打开 prompt 就看到约束和术语，直接出方案。Round 1 耗时从 20 分钟降到 3 分钟。

【切换到 Obsidian。】

而且这套沉淀是**全自动的**——项目交付后，技术决策自动提取、自动打标、自动归类；分类规则由知识库自己定义，加一个新主题就是加一篇文档，不用改一行代码；暂时归不了类的知识自动归档，等知识库长大后再自动归位。每个任务还带着知识引用链——计划引用了哪些知识文档、实现有没有真用上，交付时都能度量。一句话：知识库不是你维护的，是项目跑出来的。

这是一个 Obsidian Vault。我现场写一个需求：用户列表加 CSV 导出。就写三行描述，四条完成标准——【键入内容】——保存。

【等待 2-3 秒，切换到终端或展示通知。】

daemon 检测到变更——自动创建了 TASK 文件。我补一行 assignee——保存。

【播放录制或展示 Round 1 结果——提前准备好截图/timelapse。】

daemon 检测到变更——自动创建了 TASK 文件。我补一行 assignee——保存。

【展示通知或 Kitty tab。】

AI 检测到需求有模糊点——自动弹出 Grilling 对话。我切到新 tab，回答了 5 个问题——审批几级、超时策略、驳回路径——对齐完成。

【保持当前 tab 不动，再触发一次 watcher 或展示预录片段。】

这里我故意再触发一次。注意——没有第二个 Grilling tab。系统识别的是 TASK 身份，不是一次性的通知：owner 防止重复对话，Kitty 去重防止重复入口。即使终端返回异常数据，它也会选择不冒险开新 tab，改用桌面提醒，下一轮再重试。

【展示 Round 1 结果。】

AI 出了实现计划。五个步骤，每步有目标、有产出物、有验收映射。还提了一个 ADR——架构决策记录——"审批状态使用事件溯源"。我审一眼——"嗯，和我想的一样"。
PR 创建了，合并了。完成。

从需求到合并——【停顿】——4 小时。

【切到 Dashboard。】

最后看一个东西——这是我们项目的任务看板。这个是"ADR 提议待审"——AI 提议的架构决策，排在这里等你批准。你不设 `adr_approved: true`，它不会写入。这个是"架构决策记录"——每个项目自动长出来的 ADR 目录。

【停顿。】

这不是 PPT——这是真实在跑的系统。每个项目自动积累知识——共享词汇、设计模式、踩过的坑。不是一个工具在记录，是整个项目在生长。

## Slide 16.5: 文档质量体系

【翻页。】

还有一件事我们花了大力气——文档防腐。

大家写项目都知道，时间长了文档会烂——CONTEXT.md 没人更新，ADR 写了一次就忘了，甚至有个 `<id>` 标签把 Obsidian 渲染搞挂了——排查半天才发现是 Markdown 解析问题。

我们做了五层防护。【逐层指向屏幕】。

第一层——写入即校验。改任何 frontmatter 都要 validate-before-write。OMP 跑完一轮后，daemon 用 git diff 扫描所有变动的 .md 文件——包括 CONTEXT.md、Notes/adr/——谁坏了立刻通知你。不是只盯着 TASK 文件。

第二层——自动修复。双引号里面有中文引号把 YAML 搞挂了？repair-doc 找出来修好。body 里写了 `<id>` 被 Obsidian 当 HTML 标签不渲染？repair-doc 自动转成 `\<id\>`。连 frontmatter 结尾 `---` 丢了都能修——正文里的 `##` 标题、表格、block scalar 全部保留。

第三层——ADR 原子写入。重大架构决策不是人肉写到 Notes 目录——otg write-adr 走的是和 update-status 同款的原子写——tmp 写入、fsync、rename——写到一半断电也不出半截文件。

第四层——CONTEXT.md 自动维护。Round 1 出计划时发现新术语——追加。Round 2 写 ADR 引入新概念——追加。append-only，不覆盖。

第五层——上下文注入。daemon 在调度 OMP 之前，从 CONTEXT.md 提取约束、反模式、相关领域术语和 ADR 摘要，注入到 prompt 头部。agent 第一屏就看到项目边界——不用再手动读文件。控制在 ~300 token，每轮对话都有。

## Slide 14: 信任建立路线图

【翻页。】

演示完了。你们可能会想——"看起来不错，但我怎么开始用？是不是第一天就要把核心业务交给 AI？"

不是。我的建议是这样的——

第一周，跑一个无害任务。"把按钮颜色改成蓝色"。零风险，但你完整体验了流程。

第二周，跑一个低风险任务。"加一个 last_login_at 字段"。验证代码质量。

第三周，跑一个中等任务。"CSV 导出功能"。从需求到 PR 完整链路。

第四周开始，日常使用。核心逻辑——人写，AI review。重复 CRUD——AI 写，人 review。探索提问——AI 出方案，人决策。

信任不是讲出来的——是跑出来的。

## Slide 22: 三个带走的原则

【翻页。这是收尾的关键 Slide。】

好——【停顿】——说实话。

【停顿 2 秒。】

今天在座的各位，大部分不会装 Obsidian Task Runner。可能因为你不用 Linux，可能因为你不用 Obsidian，可能因为你们团队有自己的工具链，换不动。

这没关系。

我今天讲的——不是一个工具。我讲的是"人 + AI 协作"的几个原则。这几个原则——你明天就能用，不需要装任何东西。

【指向第一张卡片。】

第一，写好需求。需求 = 谁用 + 什么场景 + 验收标准 + 不做的事。不需要工具——多花 3 分钟写清楚。不管执行者是人还是 AI，返工都会少。

【指向第二张卡片。】

第二，建立 Gate。任何 AI 参与的工作——必须有一个显式的"人看了、确认了"的节点。不需要工具——只需要一条团队规则。没有确认点的自动化，就是没有刹车的车。

【指向第三张卡片。】

第三，积累知识。把你项目的决策和坑写进 CONTEXT.md + ADR + 知识库。不为了今天——为了三个月后的你，和下一个接手的人。不需要工具——只需要你动笔。三个月后的你，会感谢今天的你。

【停顿。】

这三个习惯——比任何一个工具都更重要。

工具会变，原则不会变。
