## 缺了什么：四个"缺角"

### 缺角一：项目记忆 = 复利效应 🧠 → 💰

**为什么缺这个很致命**

OTR 有一个在主流 AI 编码工具中普遍缺失的能力——**项目累积记忆（memory.md）**。每次任务结束后，AI 自动记录：为什么选方案 A、遇到了什么坑、项目有什么特殊约定。下次任务先读记忆，相当于"AI 越用越懂你的项目"。

但这个能力在现有演讲材料里**只占据不到 3 行**（slides Slide 10、requirement-writing-guide 里一笔带过）。它应该是演讲的高潮之一。

**建议补充内容**

```
## 演讲附加模块：项目记忆的复利效应（建议插在 Demo 之后，3 分钟）

### 类比开场

"你们团队有没有那种'老法师'——项目有什么坑、为什么当年选了
这个方案而不是那个方案，全在他脑子里？他一休假，团队就抓瞎。

OTR 的项目记忆，就是把'老法师的脑子'写成文档，而且是自动的。"

### 用一个对比说明

第一个任务：TASK-001 用户登录
  Round 1: AI 花 20 分钟读代码、理解项目结构
  → 生成的 memory.md:
    "项目使用 JWT + refresh token 双 token 模式"
    "middleware 统一处理 auth，不要在 handler 里重复验证"
    "测试用 testify/suite，每个 suite 自己起 test DB"

第十个任务：TASK-010 操作审计日志
  Round 1: AI 先读 memory.md（30 秒）
  → "已知：JWT 鉴权在 middleware 层、测试用 testify/suite"
  → 直接出方案，不需要重复探索

### 关键数字（如果有数据最好，没有就用叙事）
  TASK-001: Round 1 耗时 ~20 分钟（大部分在理解项目）
  TASK-010: Round 1 耗时 ~3 分钟（memory.md 提供了 80% 的上下文）

### 收尾句
"Cursor 每次都从头开始。OTR 每次都在上次的基础上继续。
这不是工具，这是会积累经验的团队成员。"
```

**应该放哪**：
- 在 20 分钟版中：Demo 之后、架构之前（17:00 前后），2-3 分钟
- 在 30 分钟版中：作为独立模块，5 分钟，包含一个真实的 memory.md 截图
- 在 slides 中：Slide 10 已有但内容太弱，建议拆成两张 Slide——一张讲"是什么"，一张讲"复利效应"


### 缺角二：组织级影响 —— 不是个人工具，是团队能力

**为什么缺这个很致命**

现有材料讲了很多"对你个人有什么好处"，但对于推广来说，**决策者（Tech Lead / CTO / 总监）需要听到的是"对团队有什么好处"**。目前 slides Slide 7 有一个"你的角色：决策者"的对比，但只讲了个人角色的变化，没有讲团队层面的变化。

**建议补充内容**

```
## 建议新增 Slide：团队工作方式的变化（插在 Demo 之后、架构之前）

          过去                              用 OTR 后
  ┌──────────────────┐              ┌──────────────────┐
  │ 周一站会           │              │ 周一站会           │
  │ "导出功能谁做？"    │              │ "小林提的导出需求    │
  │ "我来吧，估计 3 天" │              │  AI 已经出了方案，   │
  │                    │              │  大家看下方向对不对" │
  └──────────────────┘              └──────────────────┘
           │                                   │
           ▼                                   ▼
  ┌──────────────────┐              ┌──────────────────┐
  │ 开发时间分配       │              │ 开发时间分配       │
  │ 🟦🟦🟦🟦 写 CRUD    │              │ 🟦 写 CRUD        │
  │ 🟨🟨 写测试        │              │ 🟨🟨🟨🟨🟨 Review  │
  │ 🟩 Review         │              │ 🟩🟩🟩 架构设计    │
  └──────────────────┘              └──────────────────┘

  关键转变：
  - 开发从"执行者"变成"审查者 + 架构师"
  - PM 从"口述需求"变成"写需求文档"（减少信息衰减）
  - 新人 onboarding：读 memory.md 比问老员工更快、更准
  - 知识沉淀：不再依赖"那个知道的人"
```

**演讲台词**：

> "我们推广 OTR 不是为了替代开发者——是为了把开发者从'翻译需求到代码'的重复劳动里解放出来，让他们把时间花在 review、架构设计、攻克复杂问题上。这不是裁员工具，这是让团队做更有价值工作的工具。"

**应该放哪**：
- 在 Demo 展示完"看，AI 真的能做"之后
- 因为 Demo 展示的是**个体能力**，紧接着的应该是**团队影响**——把个体故事拉高到组织层面


### 缺角三：信任建立路线图 —— "我怎么知道能信它？"

**为什么缺这个很致命**

推广一个新工具最大的障碍不是功能不够，是**信任不够**。现有材料讲了三个 Gate 的安全机制，但没有讲**怎么从零开始建立信任**——一个团队不会第一天就把核心业务交给 AI。

**建议补充内容**

```
## 建议新增 Slide：信任建立路线图（插在安全边界 Slide 之后）

  第 1 周：跑一个"无害任务"
    "把登录按钮颜色改成蓝色"
    → 感受流程，建立对"三个 Gate"的直觉

  第 2 周：跑一个"低风险任务"
    "给用户表加一个 last_login_at 字段"
    → 验证代码质量，养成 review 习惯

  第 3 周：跑一个"中等任务"
    "加 CSV 导出功能"
    → 从需求到 PR 的完整链路

  第 4 周+：日常使用
    - 核心业务逻辑：人工写，AI review（反向使用）
    - 重复性 CRUD：AI 写，人工 review
    - 探索性提问：AI 出方案，人工决策

  信任不是"我相信 AI 写的每一行代码"
  信任是"我相信这个流程——AI 写、测试验证、人工 review
  ——三关下来不会出大问题"
```

**演讲台词**：

> "我不会建议你第一天就把支付模块交给 AI。从改个按钮颜色开始——没有风险，但你能完整体验整个流程。一周后你觉得舒服了，再试个更复杂的。信任是跑出来的，不是讲出来的。"

**应该放哪**：
- 安全边界 Slide 之后，安装 Slide 之前
- 这是一座桥——从"这东西安全吗"到"我怎么开始用"


### 缺角四：成功指标 —— "用了之后怎么知道值不值？"

**为什么缺这个很致命**

管理者做决策需要 ROI 判断，但现有材料没有提供任何衡量标准。结果就是：听完觉得好，但回去无法向上汇报"为什么我们应该投入"。

**建议补充内容**

```
## 建议新增 Slide：怎么衡量 OTR 的价值（插在总结之前）

  不需要等三个月——从第一个任务就能看到数据：

  | 指标 | 怎么算 | 从哪看 |
  |------|--------|--------|
  | 需求→PR 时间 | 需求创建到 PR 合并的时间差 | Git log + TASK 文件时间戳 |
  | 人工耗时 | 你实际花在任务上的时间 | TASK 的 actual_hours 字段 |
  | AI 首轮准确率 | Round 1 计划被直接批准的比例 | TASK 的 plan_version（v1 被批准 = 首轮准确） |
  | 知识沉淀量 | References/ 知识库文档数（core/extended/archived） | `otg kb search` / `References/INDEX.md` |
  | 开发者满意度 | 由"写 CRUD"变成"review + 架构"的比例 | 团队 survey |

  量化示例（⚠️ 示意数据，请在积累 10+ 任务后用实际统计替换）：
    需求→PR 中位时间: 4h（vs 传统 ~48h）
    人工耗时中位数: 15min（vs 传统 ~2h）
    AI 首轮准确率: 70%（越往后越高）
```

**应该放哪**：
- 总结 Slide 之前，作为"回去之后怎么汇报"的弹药
- 或者作为备用 Slide，在 Q&A 被问到"怎么衡量 ROI"时切出来

如果只加一个模块，加哪个？

## 缺角已修复：知识库技能（2026-07-28）

### 缺角一（项目记忆的复利效应）→ 已升级为知识库技能

原建议："项目累积记忆（memory.md）应该是演讲高潮"。现已升级为：

- **不再是 memory.md**：改为分层知识库 `References/`（core/extended/archived），60+ 篇文档全部带标准 frontmatter
- **双向流动**：项目 ADR/实现经验 → 自动提取到知识库；知识库内容 → Agent 查询时优先检索
- **实践验证**：`verified: true/false` 标记，只有被项目实践证实的知识才翻 true
- **slides 中已补充**：Slide 12（知识库技能）+ Slide 12.5（双向流动）

### 缺角二（组织级影响）→ 知识库是团队能力的基石

知识库使 OTR 从"个人工具"变为"团队资产"：
- 新人不需要问老员工 → 知识库有已验证的最佳实践
- 项目交接不依赖口头传承 → ADR + 验收记录自动回流
- 跨项目经验复用 → 三个项目都选了 Connect+Wire → 标注为强推荐模式

| 亮点 | 一句话 | 对应 Slide |
|---|---|---|
| **零手动流水线** | "写需求 → 自动计划 → 自动写代码 → 一次对话 + 两次确认" | Slide 4-5 |
| **知识从项目中长出来** | "不是手动维护 wiki——代码写完了，知识自动入库" | Slide 12.5 |

### 💡 技术向亮点（30 分钟版展开）

| 亮点 | 卖点 |
|---|---|
| 单一 Go 二进制 (5.3MB) | "没有 Python 依赖、没有 Docker、没有数据库。systemd 丢进去就跑。" |
| task-path flock + Grilling heartbeat lease | "同一个 TASK 不会被两个 AI 同时改。Crash 了 30 分钟自动恢复。" |
| 声明式 Scaffold Intent | "想建新项目？写 `kind: go-microservice, capabilities: [k8s]`——AI 出方案，你确认了就建。" |
| Priority Assessment 三维自动评分 | "不是手动排 P0-P4——AI 读完需求自动判断影响面、紧迫度和替代方案。" |
| 需求三分类收敛（v0.23+） | "事实类自动修正、有建议的低风险项自动采纳留审计、只有真争议才问人——不拿琐碎问题烦你。" |
| 项目级决策清单（v0.23+） | "同一需求多个任务的重复问题自动合并，争议攒一批你一次答完，答案自动分发回各需求——不再逐任务重复弹窗。" |
| 文档从不腐烂 | "每次 AI 改完 frontmatter 先校验再写入。写坏了自动检测，修好了才落盘。" |

### ⚡ 被低估的亮点（当前材料没充分展开，建议加强）

1. **Grilling 交互设计**：自动弹 Kitty tab、同 TASK 不重复、heartbeat 防超时——这是"人机协作"的工程化实践，不是简单的 chatbot
2. **Declarative Scaffold**：`kind + capabilities` 比"选模板"高级一个维度——用户表达意图，AI 出方案
3. **REQ hash 门禁**：需求改了 → AI 不会基于旧需求执行——这个安全细节值得单独 30 秒
4. **off_peak_only**："深夜跑可以省 70% token 费"——财务决策者会记住这个数字
5. **Shape Up 方法论支撑**：OTR 的 scope hammering、appetite、closed "不下注就丢弃" 都源自 Basecamp 的工程实践——不是拍脑袋设计的，是有理论基础的自动化
