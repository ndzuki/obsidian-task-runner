# 如何写好需求：让 AI Agent 准确理解并实现你的想法

> 写给 Obsidian Task Runner 的所有用户——无论你会不会写代码。
> 需求写得好，AI 出方案精准、实现少走弯路；需求写得模糊，AI 只能靠猜，结果像抽卡。

---

## 一、核心认知：AI 读需求，和人不一样

### 你写给人类开发时……

```
你：  "加个 CSV 导出"

开发：（心里想）哦，和上次那个 Excel 导出差不多吧，字段应该一样，
      编码 UTF-8，文件名带日期，最多导多少条？不管了先按 5000 做。
      —— 因为你们团队昨天刚讨论过"导出要加上限"。
```

人类开发有**共享上下文**——团队约定、历史决策、走廊聊天、代码库惯例。很多东西不用说。

### 你写给 AI 时……

```
你：  "加个 CSV 导出"

AI：  （心里想）什么数据？哪些字段？什么编码？文件名叫什么？
      有没有行数限制？要不要 BOM？Excel 兼容吗？
      用户怎么触发？API 还是按钮？权限怎么控制？
      —— AI 没有任何共享上下文，它只能从你的文字里推断。
```

### 关键原则

> **把 AI 当作一个非常聪明、但今天是第一天入职且从没参加过你们团队任何会议的新同事。**

你需要把"你以为大家都知道"的东西写下来。这不是啰嗦——这是给 AI 提供它唯一的信息来源。

## 二、好需求的三个层次：从"能用"到"好用"

```
L1 极简           L2 标准             L3 完整
────────         ─────────          ─────────
要做什么           要做什么             要做什么
完成标准           完成标准             完成标准
                  背景                 背景
                  功能列表             功能列表（含 Given/When/Then）
                  技术约束             技术约束
                                      非功能性需求
                                      API 规格
                                      数据模型
                                      依赖 & 风险

越往右，AI 越不需要"猜"。但花的时间也越多。
选哪一档？下面有决策树。
```

### 什么时候用 L1 极简？

```
✅ 简单改动（改文案、加字段、修 bug）
✅ 探索性提问（"如果做 X 会怎样？"先看方案再细化）
✅ 你信任 AI 的技术判断（项目 CONTEXT.md / 知识库已积累足够上下文）

示例：
  ## 要做什么
  把登录页的按钮文案从"登录"改成"立即登录"。

  ## 完成标准
  - [ ] 按钮文案变为"立即登录"
  - [ ] 颜色、位置不变
```

### 什么时候用 L2 标准？

```
✅ 新功能或中等复杂度改动
✅ 有明确的技术约束需要遵守
✅ 需要和团队其他人对齐理解
✅ 这是你日常最常用的档位

示例见下方 Section 四。
```

### 什么时候用 L3 完整？

```
✅ 跨系统集成（外部 API、消息队列、数据库迁移）
✅ 有严格的性能/安全要求
✅ 团队评审需要完整的规格文档
✅ 你想在 Round 1 就看到非常精准的计划，减少返工

不需要每次都 L3——大部分需求 L2 就够了。
```

## 三、写好需求的五个思考步骤

不要一上来就填模板。先想清楚这五个问题——顺序很重要。

### Step 1: 谁、什么问题、为什么

```
❌ 跳过的后果：AI 不知道这个功能给谁用、解决什么场景，可能做出"技术上正确但没人用"的东西。

✅ 写下来：
  - 谁会用这个功能？（角色：运营、客户、管理员？）
  - 他们现在怎么做这件事？（手动导出 SQL？每次都找开发？）
  - 做完之后他们的体验有什么变化？
```

**不用写成长篇大论**，一两句话就行。但这个信息会改变 AI 的很多设计决策。

```
示例：
  ## 背景
  运营团队每次需要用户数据做周报，都要找开发手动跑 SQL 导出。
  做一个自助 CSV 导出功能，让运营自己在后台操作。
  目标用户：运营（非技术），每周使用 1-2 次。
```

> 有了这段背景，AI 在选择方案时会倾向于"简单、有明确 UI 按钮、Excel 兼容"，而不是"提供 API 端点让运营用 curl 调"。

### Step 2: 画出边界——什么做，什么不做

```
❌ 跳过的后果：AI 容易过度设计。"加个导出"可能变成"做一个完整的报表系统"。

✅ 写下来：
  - 做什么：功能的核心范围
  - 不做什么：明确排除的内容（哪怕你觉得"显然不做"）
```

```
示例：
  ## 范围
  做：
  - 用户列表页增加"导出 CSV"按钮
  - 导出全量字段 or 当前筛选结果

  不做（本期）：
  - 不支持 Excel 格式（.xlsx）
  - 不支持自定义字段选择
  - 不支持定时自动导出
  - 不考虑超过 10000 条的场景（前端给提示）
```

### Step 3: 定义"做完"的标准

```
❌ 跳过的后果：AI 不知道做到什么程度算完成。可能实现了一部分就停了，
  或者花了太多时间在一个细节上。

✅ 写下来：具体的、可验证的完成条件。每条用 - [ ] 开头。
```

```
示例：
  ## 完成标准
  - [ ] 用户列表页出现"导出 CSV"按钮
  - [ ] 点击后下载文件，字段包含：id, name, email, role, created_at
  - [ ] 文件编码 UTF-8 with BOM（双击能在 Excel 正常打开中文）
  - [ ] 文件名为 用户列表_2026-07-15.csv（日期为导出当天）
  - [ ] 超过 10000 条时前端提示"数据量过大，请缩小筛选范围"
  - [ ] 导出过程中按钮显示 loading 状态
```

**每条验收标准的特点**：你可以看着最终产品说"这条过了"或"这条没过"——没有模棱两可。

### Step 4: 明确约束条件

```
❌ 跳过的后果：AI 选了一个技术上完美但不符合你环境的技术方案。
  比如用了你公司不用的库、数据库写错了、部署方式不对。

✅ 写下来：你的环境里必须遵守的限制。
```

```
示例：
  ## 技术约束
  - 后端 Go + Gin，前端 Vue 3 + TypeScript
  - 数据库 PostgreSQL（别用 SQLite）
  - 导出逻辑放后端（不在前端拼 CSV——数据量可能大）
  - 不要引入新的第三方依赖（用标准库 encoding/csv）
```

如果你不确定技术约束怎么写，**可以先空着**——AI 会读你的项目代码自行推断。但如果你知道某些约束（比如"公司规定必须用 PostgreSQL"），写下来能避免 AI 走弯路。如果完全不懂技术？跳过这节，不影响。

### Step 5: 检查"如果我是 AI，我会困惑什么"

```
❌ 跳过的后果：需求看似完整，但有隐含歧义，AI 的理解和你的意图不同。

✅ 自问：
  - 有没有词可以有多种理解？  "导出" → 下载文件？发邮件？调 API？
  - 有没有缺失的边界条件？      "权限呢？所有人都能导出吗？"
  - 有没有没说清楚的交互细节？  "按钮放哪里？导出过程中用户能看到什么？"
```

**每一处你懒得写的细节，都是 AI 必须"猜"的地方。猜对猜错，看运气。**

## 四、实战：从"一句话需求"到"AI 看得懂的需求"

### 原始需求（L1 都不到）

```
加个导出功能。
```

**问题**：导出什么？什么格式？谁用？怎么触发？AI 只能瞎猜。

### 第一轮改进（L1 极简）

```
## 要做什么
用户列表加 CSV 导出按钮。

## 完成标准
- [ ] 能下载 CSV 文件
- [ ] 包含所有用户字段
```

**问题**：进步了，但 AI 还是有很多要猜的——哪些字段？编码？文件名？行数限制？

### 第二轮改进（L2 标准 — 推荐日常使用）

```
## 背景
运营团队每周做周报需要用户数据，每次找开发跑 SQL 太慢。
做一个自助导出功能。

## 要做什么
用户列表页增加 CSV 导出按钮，运营点击后下载当前视图的用户数据。

## 功能列表
### 导出触发
- 在用户列表页工具栏增加"导出 CSV"按钮
- 按钮在有数据时可用，无数据时置灰

### 导出内容
- 字段：id, name, email, role, created_at, status
- 字段顺序与用户列表表头一致
- 仅导出当前筛选/搜索条件下的结果（非全量）

### 文件格式
- CSV 格式，逗号分隔
- UTF-8 with BOM 编码
- 第一行为列名（中文）
- 文件名格式：用户列表_2026-07-15.csv

### 边界处理
- 导出超过 10000 条时，前端弹窗提示并阻止
- 导出中按钮显示 loading，导出完成后恢复

## 完成标准
- [ ] 工具栏出现"导出 CSV"按钮
- [ ] 导出的 CSV 包含 6 个字段，顺序正确
- [ ] 文件名包含当天日期
- [ ] Excel 双击打开中文不乱码
- [ ] 筛选后导出仅包含筛选结果
- [ ] 超过 10000 条时弹出提示不下载
- [ ] 导出中按钮不可重复点击

## 不做（本期）
- 不支持自定义字段选择
- 不支持 Excel (.xlsx)
- 不支持异步导出（大数据量场景）
```

**为什么这样写更好？**

| 原始需求 | 改进后 | AI 的效果差异 |
|---------|--------|-------------|
| "导出" | "CSV 下载" + "按钮在工具栏" | AI 不会建 API 端点等你调，而是直接做按钮+下载 |
| 没说编码 | "UTF-8 with BOM" | AI 不会导出后运营发现中文乱码 |
| 没说范围 | "当前筛选结果" + "不超过 10000" | AI 不会纠结要不要做全量异步导出 |
| 没说文件名 | "用户列表_日期.csv" | AI 不会用 `export.csv` 这种毫无意义的命名 |
| 没说不做什么 | "不做自定义字段" | AI 不会过度设计字段选择器 |

## 五、常见需求类型的写法和模板

### 类型 A：Bug 修复

```
## 背景
（什么情况下出现这个 bug？影响哪些用户？有截图或日志更好）

## 复现步骤
1. 打开用户列表页
2. 筛选"状态=已删除"
3. 点击分页第 2 页
→ 实际：显示"暂无数据"（实际有 15 条已删除用户）
→ 预期：正确显示第 2 页数据

## 完成标准
- [ ] 筛选已删除用户后分页正常
- [ ] 任何筛选项 + 分页组合都正常
- [ ] 添加回归测试覆盖此场景
```

**要点**：复现步骤是 AI 理解 bug 的最快方式。能写"实际 vs 预期"的对比就写。

### 类型 B：新 API 端点

```
## 要做什么
新增 GET /api/users/export，返回 CSV 文件流。

## API 规格
GET /api/users/export?status=active&role=admin&limit=10000
Header: Authorization: Bearer <token>

Response 200:
  Content-Type: text/csv; charset=utf-8
  Content-Disposition: attachment; filename="用户列表_2026-07-15.csv"

Response 400:
  { "error": "limit_exceeded", "message": "最多导出 10000 条" }

Response 401:
  { "error": "unauthorized" }

## 完成标准
- [ ] 接口接受 status、role、limit 三个可选查询参数
- [ ] limit 默认 10000，超过返回 400
- [ ] 仅导出当前用户有权限查看的数据
- [ ] 响应 Content-Type 和 Content-Disposition 正确
- [ ] 添加接口测试
```

**要点**：如果你会写 API 规格，直接写——这是 AI 最喜欢的格式。不需要完全符合 OpenAPI 规范，伪代码也行。

### 类型 C：UI 改动

```
## 要做什么
用户列表页的操作栏增加"导出 CSV"按钮。

## 改动位置
- 文件：src/views/UserList.vue
- 位置：搜索框右侧，与"新增用户"按钮同级

## 交互细节
- 按钮文案："导出 CSV"，图标 📥
- 点击 → 按钮变 loading → 调 API → 下载 → 恢复
- API 报错 → 顶部弹出红色错误提示（3 秒自动消失）
- 成功 → 顶部弹出绿色成功提示"导出成功，共 1234 条"

## 完成标准
- [ ] 按钮在搜索框右侧显示
- [ ] 权限：仅 admin 和 operator 角色可见
- [ ] loading 状态正确（不可重复点击）
- [ ] 成功/失败提示正确
```

### 类型 D：新项目脚手架

```
## 要做什么
创建一个 Go 后端服务脚手架，用于用户管理系统。

## 技术选型
- Go 1.24+
- HTTP: Gin
- 数据库: PostgreSQL
- 配置: Viper
- 日志: slog
- 部署: Docker + Kustomize

## 目录结构期望
（如果你有偏好的目录结构就写，没有就留空让 AI 推荐）

## 初始功能
- [ ] `GET /health` 健康检查
- [ ] `GET /ready` 就绪检查（含 DB ping）
- [ ] 统一错误处理中间件
- [ ] 请求日志中间件
- [ ] Makefile（build / test / lint / run）
- [ ] .golangci.yml
- [ ] Dockerfile
```

**要点**：新项目最重要的是写清楚技术选型和初始功能边界——Round 1 只会出方案，不创建文件，放心写。

### 类型 E：数据分析/报表

```
## 要做什么
每周一早上 9:00 自动发邮件给运营团队，汇总上周新增用户数据。

## 输出内容
邮件正文包含：
- 上周新增用户总数
- 按来源渠道分组（自然流量、付费广告、邀请）
- 与前一周的环比变化（↑12% 或 ↓5%）

## 技术约束
- 定时任务不要用 cron（用 systemd timer）
- 发邮件用公司已有的 sendgrid 封装
- 统计 SQL 要考虑时区（Asia/Shanghai）

## 完成标准
- [ ] 每周一 9:00 自动发送
- [ ] 邮件格式正确，数据准确
- [ ] 如果数据查询失败，不发邮件但记录日志告警
```

## 六、最常犯的五个错误（及修复）

### 错误 1："加个 XX 功能"

```
❌ 太模糊，AI 有 100 种理解方式

✅ 至少补一句"要做什么"：
   "用户列表页加 CSV 导出按钮，运营点击后下载"
```

### 错误 2：把实现细节写进需求

```
❌ 功能需求里写实现方式：
   "用 goroutine pool 并发查询，channel 传结果，
    用 sync.WaitGroup 等所有 goroutine 完成"

✅ 技术约束里写限制，功能需求里写产出：
   ## 要做什么
   查询 100 个数据源，10 秒内返回聚合结果

   ## 技术约束
   - 必须并发查询（Go 实现）
   - 不能引入外部消息队列
```

**为什么**：你写的是"怎么做"而不是"做什么"。AI 可能有更优雅的实现方式，但你的需求把它锁死了。把实现留给 AI，你只需要说清楚"产出是什么、限制是什么"。

### 错误 3：验收标准写得太抽象

```
❌ "性能好"、"用户体验好"、"代码质量高"

✅ "P99 延迟 < 100ms"
✅ "按钮点击后 200ms 内出现 loading 状态"
✅ "通过 golangci-lint 全部规则"
```

**原则**：验收标准应该是**可观测的行为或可测量的指标**。如果你看着最终产品无法斩钉截铁地说"通过"或"不通过"，这条标准就需要重写。

### 错误 4：不写"不做什么"

```
❌ AI 看到"加导出" → 做了 CSV + Excel + PDF + 定时 + 字段定制 + 权限控制

✅ ## 不做（本期）
   - 不支持 Excel
   - 不支持定时导出
   - 不支持自定义字段
```

**为什么**：AI 会倾向于做得完整。你不画边界，AI 就帮你画。等 Round 2 出来你发现做了一个礼拜的工作量时，已经晚了。

### 错误 5："我觉得这个很明显，不用写"

```
❌ 你心里想："当然只导出当前筛选结果啊"
   AI 收到的需求：没说筛选范围 → AI 做了全量导出

✅ 所有"你以为显然"的东西，都是 AI 不知道的东西。
   写下来。一行字的事。
```

## 七、写需求前的自检清单

保存需求文件之前，花 1 分钟过一遍：

```
□ 谁用？
  └ 有没有说清楚目标用户是谁？

□ 什么场景？
  └ 有没有描述用户在什么情况下需要这个功能？

□ 边界清晰吗？
  └ 有没有写"做什么"和"不做什么"？

□ 验收标准可验证吗？
  └ 每条 - [ ] 能不能看着最终产品说"通过/不通过"？

□ 我不写谁会困惑？
  └ 有没有隐含假设没写出来？（"当然是用 PostgreSQL 啊" → 写下来）

□ 有没有写实现方式而不是产出？
  └ 删除"怎么做"的描述，保留"做什么"和"约束条件"

□ 如果这个需求明天交给一个完全不了解项目的人，他能理解吗？
  └ 这就是 AI 看到你需求时的状态。
```

## 八、渐进式需求：不需要一次写完

你不需要一开始就写 L3 完整需求。更好的方式是：

```
第一版（L1 极简）：
  写"要做什么" + "完成标准" → 保存 → Round 1 出方案

审阅 AI 的计划：
  → "嗯，Step 3 不是我想要的" → 回需求文档补充"功能列表"细节
  → 需求变更触发重新出计划，但这次更精准

第二版（L2 标准）：
  补充了字段列表、交互细节、边界处理 → 再出方案
  → 这次的计划应该接近你想要的

（如果需要）第三版（加技术约束）：
  补充"不要引入新依赖"、"必须用 PostgreSQL" → 最终版方案
```

**核心理念**：先让 AI 出一版方案，看看它理解对了多少。哪里理解偏了，就在需求里补哪里。比你一开始试图想清楚所有细节要高效得多。

这也是 OTR 的"需求变更自动重新出计划"机制的设计初衷——**不是让你一开始就写完美需求，而是让你在迭代中逼近精准。**
