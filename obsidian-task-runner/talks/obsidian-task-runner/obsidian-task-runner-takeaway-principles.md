# 如果不用 OTR，你也能带走的启发

> 演讲收尾模块。坦率承认不是每个人都会用这个工具——但每个人都能从中学到东西。


## 诚实开场（建议放在总结 Slide 之前，1 分钟）

```
（过渡：前面花了 17 分钟讲 OTR 有多好——现在我要告诉你们一件更重要的事）

"说实话——今天在座的各位，大部分人不会装 Obsidian Task Runner。

可能因为你不用 Linux，可能因为你不用 Obsidian，
可能因为你们团队有自己的工具链，换不动。

这没关系。我今天讲的不是一个工具——
我讲的是'人 + AI 协作'的几个原则。
这几个原则，你明天就能用，不需要装任何东西。"
```


## 三个带走的原则

### 原则一：需求文档是第一公民

```
传统思维：                    新思维：
"写个 ticket，剩下的          "把需求写清楚，AI（或开发者）
 开发者会搞定"                 就能一次做对"
```

| 你现在的做法 | 改进后的做法 | 为什么更好 |
|-------------|-------------|-----------|
| Jira 标题："加 CSV 导出" | 补充：导出哪些字段、什么编码、文件名格式、行数上限 | 开发者不需要来回问 4 个问题 |
| 口头说："做个报表" | 写下来：谁看、什么数据、什么频率 | 一个人理解的需求不会在传话中变形 |
| "需求就是标题" | "需求 = 背景 + 范围 + 验收标准 + 不做的事" | AI 或新人不需要猜 |

**明天就能做的事**：
下一张 Jira ticket 或 PRD，至少写四样东西——**谁用、什么场景、完成标准、不做什么**。不需要装任何工具。

### 原则二：所有流程都需要"确认点"

```
OTR 的三个 Gate 不是 OTR 独有的——它是"人 + AI 协作"的通用模式：

  任何 AI 辅助的工作流，都应该有显式的"人工确认点"

  自动化步骤          人工确认点
  ─────────          ─────────
  AI 出设计方案    →  人审方案（方向对不对？）
  AI 写代码        →  人审代码（质量过不过？）
  AI 写文档        →  人审内容（有没有胡说？）
  AI 做数据分析    →  人审结论（逻辑通不通？）

  没有确认点的自动化 = 没有刹车的车
```

**明天就能做的事**：
如果你们团队在用 Cursor / Copilot，加一条简单规则：**AI 写的代码必须在 PR review 时明确标注，review 人要比人工代码多看一遍**。这就是你的第一个 Gate。

### 原则三：团队记忆是 AI 时代的核心竞争力

```
你现在的团队记忆在哪？
  □ 老员工的脑子里（他一休假就抓瞎）
  □ Slack / 飞书聊天记录里（三个月后就搜不到了）
  □ 散落在各个 PR description 里
  □ 没有。每次新人来都从头问。

OTR 的 CONTEXT.md + ADR + 知识库给了我们一个启发：

  ┌─────────────────────────────────────────────┐
  │ 每个项目维护一个"决策日志"                   │
  │                                             │
  │ 记录了：                                    │
  │  - 为什么选了方案 A 而不是 B？               │
  │  - 有哪些坑（以及怎么绕开的）？              │
  │  - 项目有什么特殊约定？                      │
  │                                             │
  │ AI 读它 → 更精准                             │
  │ 新人读它 → 更快上手                          │
  │ PM 读它 → 知道什么是可行的                    │
  │ 三个月后的你读它 → 知道自己当时为什么这么写   │
  └─────────────────────────────────────────────┘
```

**明天就能做的事**：
在你的项目里建一个决策日志——叫 `docs/decisions.md`、`adr/`、`design-notes.md` 都行，关键是有一个地方记录决策。每次做技术决策时加一段：
```
## 2026-07-15: 选择 PostgreSQL 而不是 MySQL
- 原因：团队更熟悉 PG，已有运维脚本
- 替代方案：MySQL 8.0，但因为 xxx 放弃
- 影响：后续的 JSON 查询可以直接用 PG 原生支持
```
不需要 AI，不需要工具——只需要一个 markdown 文件。

## 按角色分：你明天可以做什么

### 如果你是 PM

```
明天就能做的三件事：

1. 下一份 PRD，用"背景 + 范围 + 验收标准"三段式
   → 开发不会再问"这个场景要不要覆盖？"

2. 加一栏"不做的事"
   → 开发不会再过度设计了

3. 验收标准写成"能/不能"判断
   → "性能好" → "P99 < 100ms"
   → "体验好" → "点击后 200ms 内出 loading"
```

### 如果你是开发者

```
明天就能做的三件事：

1. 在项目里建一个 docs/decisions.md
   → 第一个条目：解释当前技术栈为什么这么选

2. 下次 AI 生成代码后，不要直接复制粘贴
   → 先问自己："如果这是一个新人写的 PR，我会提什么 comments？"

3. 在团队里提议：所有 AI 辅助生成的代码，PR 里标注 [AI-assisted]
   → 建立"AI 写 + 人审"的肌肉记忆
```

### 如果你是 Tech Lead / 管理者

```
明天就能做的三件事：

1. 在下次团队周会上问一个问题：
   "我们团队有多少时间花在'翻译需求到代码'上？"
   → 在这个数字面前，AI 工具的 ROI 自然显现

2. 挑一个低风险任务，让团队试用任何 AI 编码工具
   → Cursor、Copilot、OTR——不纠结工具，关键是跑通"AI 写 + 人审"

3. 建立团队的知识沉淀习惯
   → 不是"写文档"，是"做决策时顺手写两行为什么这么选"
```

## 演讲收尾台词

```
（总结 Slide 之后，Q&A 之前）

"我不期望你们都用 Obsidian Task Runner。

但我希望你们带走三样东西——

第一，写好需求。需求写得越清楚，
   不管是 AI 还是开发，返工就越少。
   这不需要任何工具——只需要你多花 3 分钟写清楚。

第二，建立 Gate。任何 AI 参与的工作，
   必须有一个显式的'人看了、确认了'的节点。
   这不需要任何工具——只需要一条团队规则。

第三，积累知识。把你项目的决策和坑写进 CONTEXT.md + ADR + 知识库。
   不为了今天，为了三个月后的你和下一个接手的人。
   不需要任何工具——只需要你动笔。三个月后的你会感谢今天的你。

这三个习惯，比任何一个工具都更重要。

工具会变，原则不会变。

谢谢。"
```
