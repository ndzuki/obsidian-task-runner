# 给非技术听众的案例：PM 小林的 Obsidian Task Runner 一日

> 这个案例用于演讲中 Slide 4–6 之间，替代枯燥的功能罗列。用一个完整的人物故事，让非技术听众"看见自己"。


## 角色

**小林** — 某 SaaS 公司的产品经理。不会写代码，但每天和开发打交道。

---

## 场景一：过去 — 一个导出功能的 72 小时

```
周一 10:00  小林在 Jira 建 ticket："用户列表页加 CSV 导出按钮"
周一 14:00  开发阿强开始看 ticket，有 3 个问题在评论区问
周一 16:00  小林回复："字段是 id,name,email,created_at，编码 UTF-8"
周二 10:00  阿强开始写代码
周二 14:00  阿强："最大导出行数多少？超过怎么办？"
周二 15:00  小林："最多 10000 条，超过分页导出"
周三 10:00  阿强提 PR，另一个开发 review
周三 15:00  Review 通过，合并
周三 16:00  小林在 staging 验证 → 发现文件名格式不对，重新开 ticket

从想法到可用：72 小时
小林实际参与：回答了 4 个问题，验证了 1 次
时间都去哪了：排队等开发排期 + 异步沟通来回
```

**演讲要点**："小林的 72 小时里，真正有价值的只有两件事——'我想要什么'和'这个对不对'。中间全是等待和传话。"

---

## 场景二：现在 — 同一个需求，用 Obsidian Task Runner

```
周一 10:00  小林在 Obsidian 写下需求：

  ---
  id: "042"
  title: 用户列表 CSV 导出
  project: user-service
  priority: P2
  ---

  ## 要做什么
  用户列表页增加 CSV 导出按钮，方便运营导出数据做分析。

  ## 完成标准
  - [ ] 导出字段：id, name, email, created_at
  - [ ] 编码 UTF-8，带 BOM（方便 Excel 打开）
  - [ ] 最多 10000 条，超过时前端提示"数据量过大，请联系管理员"
  - [ ] 文件名格式：用户列表_2026-07-15.csv

        │
        ▼  保存（30 秒后）

周一 10:01  Obsidian 自动刷新 —— TASK-042 已生成
            小林补了一行 assignee: deepseek，保存

        │
        ▼

周一 10:05  💡 桌面通知："TASK-042 实现计划已生成"
            小林打开任务文件，看到 AI 出的计划：

            Step 1: 新增 GET /api/users/export?format=csv 路由
            Step 2: 实现 CSV 序列化（字段映射 + BOM）
            Step 3: 添加 10000 条上限校验
            Step 4: 文件名格式生成逻辑
            Step 5: 单元测试

            小林扫了一眼 —— "嗯，和我想的一样"
            把 plan_approved 改成 true，保存

        │
        ▼

周一 11:30  💡 桌面通知："TASK-042 代码已实现，请 review"
            小林打开 GitHub —— PR 已经在那里了
            （小林看不懂代码，但验收记录写得很清楚：
              测试: PASS
              lint: PASS
              task-verifier: 4/4 AC 全部通过）

            小林把 PR 链接发给阿强："帮我看下代码，没问题就合"
            阿强花了 5 分钟看 diff："没问题"

            小林回到 Obsidian，把 merge_approved 改成 true，保存

        │
        ▼

周一 14:00  💡 桌面通知："TASK-042 已完成合并"

从想法到合并：4 小时
小林实际参与：写需求（5 分钟）+ 确认计划（1 分钟）+ 确认合并（1 分钟）
阿强实际参与：review 代码（5 分钟）
```

---

## 三个关键变化

| 维度 | 过去 | 现在 |
|------|------|------|
| 周期 | 72 小时 | 4 小时 |
| 小林的时间投入 | 回答 4 个问题 + 验证（~30 分钟） | 写需求 + 三次确认（~10 分钟） |
| 开发的时间投入 | 写代码 + 测试 + lint（~3 小时） | review 代码（~5 分钟） |
| 沟通次数 | 4 次异步问答 | 0 次（需求文档就是沟通媒介） |
| 可追溯性 | Jira ticket + git log（分离） | 一份任务文档包含全部（计划、实现、验收、变更） |

## 小林还能做什么？

### 不只是"提需求"

```
场景 A：探索性提问
  "如果加一个导出 PDF 的功能，大概要改哪些模块？"
  → Round 1 只出计划，不写代码
  → 小林拿到一份技术评估，30 分钟就够，不需要排队等开发

场景 B：小修小补
  "把登录页的提示文案从'请输入密码'改成'请输入您的登录密码'"
  → 这种改动不值得走完整开发流程
  → 写需求 → AI 实现 → review → 合并，半小时搞定

场景 C：数据分析需求
  "运营需要每周一自动发一封邮件，汇总上周新增用户数"
  → 小林可能不知道这需要定时任务 + 数据库查询
  → 但 AI 会出方案：cron job → 查 DB → 调邮件服务
  → 小林只需要确认"是这个意思"
```

### 核心转变

```
                   过去                        现在
          ┌─────────────────┐       ┌─────────────────┐
          │  PM 想           │       │  PM 想           │
          │    ↓             │       │    ↓             │
          │  写 ticket       │       │  写需求文档       │
          │    ↓             │       │    ↓             │
          │  等开发排期       │       │  AI 出方案        │
          │    ↓             │       │    ↓             │
          │  回答开发问题     │       │  PM 确认 ✅       │
          │    ↓             │       │    ↓             │
          │  等开发写完       │       │  AI 写代码        │
          │    ↓             │       │    ↓             │
          │  验证             │       │  PM 确认 ✅       │
          │    ↓             │       │    ↓             │
          │  发现不对，重开    │       │  合并上线          │
          └─────────────────┘       └─────────────────┘

          沟通链条：PM → Dev → PM → Dev → PM    沟通链条：PM → AI → PM
          瓶颈：开发排期 + 沟通成本                 瓶颈：PM 想清楚需求的时间
```

## 在演讲中怎么讲这个案例

### 节奏安排

```
1. 先讲"场景一"（1.5 分钟）
   - 用时间线展示 72 小时的流程
   - 每一行停顿 1 秒，让听众感受等待
   - 最后一句："72 小时。其中小林真正在创造价值的，不到 10 分钟。"

2. 再讲"场景二"（2 分钟）
   - 时间线对比展示（左右分屏或上下对比）
   - 关键瞬间停留：
     * "AI 出方案" —— 给 3 秒看计划的截图
     * "PM 确认" —— 强调"只是改了一个 true"
     * "PR 自动生成" —— 展示 GitHub PR 截图
   - 收尾对比："72 小时 → 4 小时"

3. 扩展到"小林还能做什么"（1 分钟）
   - 三个场景快速过
   - 重点落在"PM 不需要会写代码，PM 只需要想清楚要什么"
```

### 视觉设计

- **场景一 vs 场景二**：用左右对比或上下对比，同比例时间线
- **时间数字要巨大**：`72h → 4h` 用最大字号，视觉冲击
- **林的角色用图标表示**：💡 = 等待 / ✍️ = 写需求 / 👀 = 确认
- **三个 gate 用钥匙图标**：🔑 Grilling 对齐 / 🔑 plan_approved / 🔑 merge_approved

### 演讲时的关键台词

> （场景一讲完后，停顿 2 秒）
>
> "72 小时不是哪个环节太慢——是每个环节都快不起来。你在等开发排期，开发在等你回问题，两边都在等对方。这不是人的问题，是流程的问题。"
>
> （场景二讲完后）
>
> "需求文档本身就是沟通媒介。AI 读得懂，AI 出方案，AI 写代码。小林做了什么？小林只做了 AI 做不了的事——判断'这是不是我想要的'。这才是 PM 真正该花时间的地方。"
>
> “而且它不会因为文件多保存了一次，就再弹一个窗口。对同一个任务，你始终只看到一个对话入口；另一个任务需要你确认时，才会有它自己的入口。系统把‘需要你决策’变成有秩序的队列，不是通知轰炸。”
>
> （收尾）
>
> "Obsidian Task Runner 给你的不是'自动写代码'，给你的是'把排队和传话的时间还给思考'。"

## 补充：不同角色的"一句话价值"

在做 Slide 时，可以给每种角色一句话，让他们立刻对号入座：

| 角色 | 一句话 |
|------|--------|
| PM | "写完需求 30 分钟看到技术方案，不用排队等开发给你评估" |
| 运营 | "'帮我加个数据看板' → 下午就能用" |
| 设计师 | "文案调整、颜色修改、简单 UI 改动——自己搞定，别等前端排期" |
| QA | "写好复现步骤，AI 帮你修 bug 并跑回归测试" |
| Tech Lead | "把重复性 CRUD 任务外包给 AI，团队聚焦架构和复杂业务" |
| CTO / 管理者 | "每行代码有记录、每个决策有依据、新人接手不需要翻三个月 Slack" |
