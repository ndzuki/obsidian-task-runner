# 离线预渲染管线

离线管线是 `cmd/prerender` 调用 `internal/{catalog,geom,render,art,sheet}` 完成的一次性批处理：把每个程序化单体在**日间**与**夜间**两套光照档下渲染成透明背景 PNG 精灵图，装箱成图集，并写出 `manifest.json` 与 `palette.json`。网页端不再做任何建模、光照或阴影计算。

```
go run ./cmd/prerender -ss 4 -out web/assets -build build
```

---

## 0. 像素密度（分辨率）

管线里所有「像素」都等于「基础像素 × `render.Scale`」。几何体一律用**格**为单位建模，
所以提高分辨率不需要改任何建模代码——`SetScale` 只做三件事：

1. `TileW/TileH/ZUnit = 32/16/8 × Scale`；
2. `art.SetTexelsPerTile(32 × Scale)`：程序化图案的纹素密度同步提高，
   「4 纹素一块砖」在 1x 与 2x 下占格子的比例完全一致；
3. `catalog.SetScale`：地形/道路/侧壁瓦片的统一画布按比例放大。

另外 `SpriteOpts.EdgeW = Scale`：轮廓描边与受光侧提亮的宽度必须跟着走，
否则分辨率越高轮廓越细，观感会变。

密度写进 `manifest.json` 的 `scale`，运行时据此配置瓦片、界面布局与帧缓冲尺寸。
`cmd/prerender -scale N` 控制离线侧，`make assets SCALE=N` 是它的包装（默认 3）：
1x/2x/3x 分别对应内部帧缓冲 640x400 / 1280x800 / 1920x1200。

离线开销随面积增长（精灵图与超采样都在涨），实测：4.5 s / 13.6 s / 27.5 s。

## 1. 投影与坐标约定

所有几何体都在**格坐标系**里建模（`1 格 = 1 单位`，Z 为高度），不做任意旋转。投影是固定 2:1 的等距**正交**投影，写在 `internal/render/render.go` 头部：

```go
const (
    TileW = 32 // 1 格 = 32x16 像素的菱形
    TileH = 16
    ZUnit = 8  // 1 高度单位 = 8 像素
)
```

屏幕映射（`Project`，屏幕 Y 向下，Z 向上为负）：

| 量 | 公式 |
| --- | --- |
| 屏幕 X | `sx = (x - y) * (TileW/2) = (x - y) * 16` |
| 屏幕 Y | `sy = (x + y) * (TileH/2) - z * ZUnit = (x + y) * 8 - z * 8` |
| 深度 | `depth = x + y + 2*z` |

`Depth` **越大越靠近相机**，Z-buffer 保留更大的值（`if d <= rs.depth[i] { return }`）。因为单个单体的尺寸远小于「深度单位」，加权的 `2*z` 只是为了在等距视角下让高处优先，真正决定同格内前后关系的是三角形本身。

投影是可逆的：屏幕坐标 → 格坐标需要沿 Z 从高到低搜索。运行时用 `view.js` 的 `pickCache` 做这件事——固定屏幕点对应的是一条斜线（z 每 +1，`x` 与 `y` 同时 +0.5），从 `MAX_HEIGHT` 往下找到第一个「该格地面高度正好等于该层」的格子即为可见地表。

**画布范围与锚点**。渲染一个单体时先在 1x 空间求出所有顶点（加阴影扫掠体、加局部原点 `(0,0,0)`）的投影包围盒，作为画布范围（`autoBounds`）；`Project` 结果减去范围的 `MinX/MinY` 得到相对画布的坐标。裁剪透明边后，锚点按 `ax = -bounds.MinX - crop.Min.X` 修正，含义是：

> **anchor = 网格局部原点 (0,0,0) 投影到图像中的像素位置。**

运行时贴图只有一次减法：

```
draw_x = originX + (x - y) * 16 - sprite.ax
draw_y = originY + (x + y) * 8 - z * 8 - sprite.ay
```

屏幕空间外扩（消除瓦片接缝）不在这里做，而是在三角形层面把顶点从重心向外推，见第 6 节。

## 2. Z-buffer 光栅化与「不剔除背面」

`drawQuad` 把每个四边形拆成两个三角形 `{0,1,2}` 与 `{0,2,3}`（退化四边形只画一个），逐像素用重心坐标插值出深度、世界坐标与图案参数，深度测试通过才写色。面朝向（`art.Face`）**不参与**剔除，只用来：

1. 推导默认明暗槽位（`shadeFromFace`）；
2. 选择 `FaceUV` 的参数化平面，保证图案不错切。

**为什么不做背面剔除。** 高度场的侧壁瓦片正是「本来看不见、抬高之后才该看见」的面：一块地台侧面在下方的格子上会直接朝向相机，但在上方的格子视角里它是背面。若按世界坐标做剔除，同一张侧壁瓦片无法在四种地形关系下复用；而且建筑的内壁、凹进的走廊、雨棚底面也会被误剔。Z-buffer 天然处理这些情况——只要多边形的绕序是确定的，深度更大者胜出。代价是必须画两倍的三角形（对离线批处理完全可以接受）。

三角形光栅化用半开区间的边函数（`eachPixel`），并先把负面积三角形交换顶点排序，保证重心坐标恒为正；边界上允许 `1e-9` 的容差，避免共享边的像素被丢弃。

## 3. 材质系统：色阶 + 朝向 + 程序化图案

一个 `Material` 只有四个字段有意义：

```go
type Material struct {
    Name    string
    Ramp    string     // 引用 97 色母板中的哪条色阶
    Shade   [4]float32 // 顶面 / 受光侧 / 背光侧 / 底面 在色阶上的位置 0..1
    Pattern string     // 程序化图案名（可为空）
    Emissive, OffRamp, Glow // 自发光相关（夜间窗户、霓虹）
    Alpha   float32
}
```

四个明暗槽位通过 `mat(name, ramp, pattern, top, left, right)` 写入，底面固定 `0.12`。明暗位置由 `art.ShadeTop / ShadeLeft / ShadeRight / ShadeBottom` 索引，`geom` 里有同名别名便于建模代码书写。

**为什么是「美术定向光照」。** 解析最终颜色的 `Renderer.resolve` 里没有任何法线、没有光源方向、没有 `dot(N,L)`：

```
明暗位置 p = Shade[朝向] * Profile.ShadeScale + 图案偏移 * PatternAmp
颜色       = 母板.Snap(Ramp, p)              // 硬边取色阶上的某一档，不改色相
```

也就是说，「这一面有多亮」是美术在材质表里手填的一个 0~1 数字，图案偏移只是在这个位置上加一点抖动。这条设计直接对应 90 年代等距美术的通行做法：**顶面最亮、朝屏幕左下的 +Y 面次之、朝屏幕右下的 +X 面最暗**。约定值大致是顶面 ≈ 0.9、受光侧 ≈ 0.5、背光侧 ≈ 0.2——在 5~6 档的色阶上正好落成「亮 / 中 / 暗」三个**分离的色调**，而不是挤在相邻两档里（那样立方体会看起来是平的）。

`internal/art/material.go` 的 `baseMaterials` 是完整的日间材质表，共 **84 个材质**（墙体 22、屋顶 10、开口 6、线脚构件 16、地面 13、植被 8、车辆 9）。`litMaterials` 是夜间替换的自发光材质，`dayExtra` 是日间档的霓虹/路灯替身。`validateProfiles()` 在 `init()` 里断言两档**材质名集合完全一致**——几何体按材质名索引，缺一个就会渲染出错。

`FaceUV` 的返回值单位是「纹素」，`1 格 = 32 纹素 = 1x 下 32 像素`。用纹素而不是世界单位，是为了让所有图案的周期都是整数像素，避免摩尔纹：

| 面 | (u, v) |
| --- | --- |
| Top / Bottom | `(x*32, y*32)` |
| PosX / NegX | `(y*32, -z*32)` |
| PosY / NegY | `(x*32, -z*32)` |

`v` 取 `-z` 是为了让图案不被上下翻转。

## 4. 图案表

`Pattern` 是一个 `func(PatCtx) float32`，返回 `[-1, 1]` 的明暗偏移；乘上 `PatternAmp = 0.15` 后叠加到色阶位置上。0.15 约等于「5 档色阶的半档」，即网点会在相邻两档之间跳，形成经典的双色抖动。网点本身来自 4x4 有序矩阵 `bayer4`（`ord(cell, u, v)`，`cell` 是网点块的边长，单位纹素）。

| 图案 | 周期 / 结构 | 用途 |
| --- | --- | --- |
| `none` | 无 | 平整面，纯平涂色块（PC-98 大色块观感） |
| `plaster` | 4x4 网点 ×0.45 | 抹灰 / 粉刷墙 |
| `concrete` | 每 8 纹素一道横向浇注缝（-0.85）+ 3x3 网点 | 混凝土墙、场地 |
| `brick` | 4x2 纹素错缝砖，水平缝 -0.9、竖缝 -0.7、砖面 2x2 网点 | 砖墙 |
| `stonewall` | 6x4 纹素大块，缝 -0.9 / -0.7，3x3 网点 | 石墙、岩壁 |
| `siding` | 每 3 纹素一道阴影线（-0.8）+ 4x4 网点 | 美式横向壁板 |
| `glass` | 每 4 纹素楼板（-0.7）+ 每 4 纹素窗框（-0.35）+ 按列 ±0.2 反射差 | 玻璃幕墙、窗 |
| `roofing` | 每 2 纹素一道横向瓦楞（-0.55）+ 2x2 网点 | 屋面油毡 / 瓦 |
| `metal` | 每 5 纹素竖向拉丝（+0.45 / -0.45）+ 2x2 网点 | 金属板、管道 |
| `asphalt` | 2x2 网点 ×0.75 + 6x6 粗颗粒（阈值 >12）+0.35 | 沥青路面 |
| `gravel` | 3x3 网点 ×0.85 + 6x6 大网点 ×0.3 | 碎石、沙地 |
| `turf` | 2x2 网点 ×0.7 + 8x8 大网点 ×0.55 | 草地（双层网点做「草丛」层次） |
| `foliage` | 4x4 网点 ×0.5 + 12x12 大网点 ×0.8 | 树冠团块 |
| `water` | 每 4 纹素波纹（+0.75 / -0.35）+ 16x8 周期的波峰高光 +0.5 | 水面（相位由 `UOff` 控制，用于逐帧动画） |
| `plank` | 每 3 纹素一道竖缝（-0.45）+ 逐像素网点 | 木料、门窗 |
| `tile` | 4x4 格缝（-0.7）+ 2x2 网点 | 瓷砖 / 马赛克 |
| `neon` | 每 3 纹素网格骨架（+0.7 / -0.3） | 霓虹招牌骨架 |
| `windowlit` | 6x6 纹素一扇窗，`Hashf` 决定亮/灭（<0.40 灭）；返回 <0 表示灭灯 | 夜间大窗 |
| `windowlit2` | 4x4 纹素一扇窗，点亮率更高（<0.30 灭） | 夜间小窗 / 住宅 |

`windowlit*` 有特殊语义：返回值 <0 表示「灭灯」，`resolve` 会改用 `OffRamp` 的暗玻璃色（`Snap(OffRamp, 0.30*ShadeScale)`）且不发光；>0 表示点亮强度，颜色取 `Snap(Ramp, (0.50 + delta*0.48) * (0.86 + 0.14*Shade[朝向]))`，并把 `Glow` 累加进自发光层。

## 5. 贴花与深度偏移（Bias）

**贴花**是贴在已有面上的、带深度偏移的水平/竖直矩形。`geom` 提供三个：

| 方法 | 面 | 用途 |
| --- | --- | --- |
| `DecalX(x, y0, y1, z0, z1, mat, bias)` | `FacePosX`，`ShadeAuto` | x=const 墙上的窗、门、招牌 |
| `DecalY(y, x0, x1, z0, z1, mat, bias)` | `FacePosY`，`ShadeAuto` | y=const 墙上的窗、门、招牌 |
| `DecalTop(z, x0, y0, x1, y1, mat, bias)` | `FaceTop`，`ShadeAuto` | 屋顶标线、场地花纹、路面虚线 |

`ShadeAuto = -1`，由 `shadeFromFace` 按面推导，于是同一个贴花在四面墙上自动获得正确的明暗。

Bias 是深度偏移，加在插值出的深度上再比较。它解决的是**共面**问题：

- `SlabTop` 自带 `Bias: 0.05`。**屋面与墙顶共面是明确的坑**：`FlatRoof`/`RoofDeck` 在 `z` 处铺屋面，而墙体的 `Box` 顶面也在 `z`，两者深度完全相同，谁先画谁就赢——这在图集里表现为「屋顶一半是墙色」，且随相机/裁剪范围变化。给屋面加固定偏移后它稳定压过墙顶。
- 门窗贴花用 `0.02 ~ 0.03`（`WindowGrid` 用 0.02，门用 0.03，招牌用 0.05）压过共面的墙。
- 路面虚线、铁路轨道用 `0.02`；路缘石是实体 `Box`，不需要偏移。
- 侧壁瓦片内部还有一层「坡脚压暗」的贴花，`Bias: 0.03`，在侧壁面上画出接地线。

由于 `Bias` 直接进深度比较，它必须远小于几何体之间的深度差（否则贴花会「穿透」到别的物体前面），也不该用于跨物体遮挡——跨物体遮挡由画家算法的绘制顺序负责。

## 6. 超采样、边缘描边 / 提亮、量化与抖动

**超采样。** 画布在 `W*ss × H*ss` 上光栅化（`make assets` 用 `ss=4`），最后用 `f×f` 盒式降采样。所有合成都在**预乘 alpha** 空间做（`art.Buf`），这样半透明阴影/辉光与抗锯齿边混合时不会出现黑边。

**屏幕空间外扩。** 地形与道路瓦片设 `Expand = 0.6`：`expandTri` 把三角形从重心向外推 `0.6*ss` 像素。等距菱形在拼接时相邻瓦片的边严格重合，光栅化的取整会让某些像素归属模糊，导致**拼缝里透出底色**。外扩让每块瓦片多覆盖一点点，缝就被后画的瓦片盖住。

**边缘处理**（`applyEdges`，在降采样之后、量化之前，作用于 1x 像素）：

| 参数 | 默认（`DefaultSpriteOpts`） | 行为 |
| --- | --- | --- |
| `Outline` | `0.42` | 4 邻域任一像素 alpha < 0.5 则把该像素压暗，压暗系数 `1 - Outline*(1-minA)`；只在自身 alpha ≥ 0.5 的像素上做 |
| `Rim` | `0.18` | 上 / 左上 / 左三个方向有透明像素 → 该像素按 `1+Rim` 提亮，给出受光侧轮廓 |
| `EdgeFade` | `0.04` | 平均 alpha 低于此值的像素直接丢弃 |
| `BinaryAlpha` | `false` | 置 true 时 alpha 二值化（<0.5 丢弃，否则 255），瓦片用 |
| `Dither` | `1` | 抖动阈值缩放（1 = 标准 8x8 有序抖动） |

**量化与抖动幅度。** `Buf.ToNRGBA` 逐像素调 `Palette.Quantize`：

```
idx = LUT[(clamp255(r*255 + thr*amp) >> 2) << 12 | ...]     // 6-6-6 最近色表
thr = Bayer8[x&7, y&7] / 64 - 0.46875                       // 值域 (-0.5, 0.5]
```

- **平涂用 7**（`Palette.Quantize` 的默认 `amp`）：幅度刻意小于「半档色阶」，保证平涂面量化回同一档，得到干净的色块；只有抗锯齿边、半透明阴影这类连续渐变才需要网点过渡。
- **渐变色用 46**（`Palette.QuantizeAmp` 显式传入）：`sheet.Sky` 画渐变天空时用接近一档色阶的幅度。若用小幅度，相邻色阶之间会出现硬边横带——在 CRT 扫描线下就是显眼的横线。

最近色查找用加权距离 `2*dr² + 4*dg² + 3*db²`（近似人眼敏感度），预先在 64³ 的 6-6-6 空间里建 LUT（约 26 万格 × 97 色比较，一次性）。**为什么是 6 位而不是 5 位**：母板里存在若干近邻色（`ink` 与 `asphalt` 的暗阶只差几个色阶），5 位截断会把它们折进同一格，母板颜色再量化一次就会漂到隔壁色上。6 位把这个约束放宽到「任意两色至少相差 4」，并有 `TestPaletteMinSeparation` 守着。建表后还会把每个母板颜色**直接钉在自己所在的格**上，保证量化往返恒等。

**辉光。** 自发光像素被写进独立的 `lit` 层；`lit.Blur(1).Blur(2)` 做两次盒式模糊（各三趟近似高斯），再以加法叠回颜色层，并给轮廓外的光晕补 alpha（`a*amt*0.85`），让辉光真的「溢出」精灵图边界。这也是建筑类精灵图 `Pad = 3`（而瓦片是 1）的原因——留出夜间辉光的空间。

**阴影。** `drawShadow` 把每个 `ShadowSrc{底面矩形, z0..z1}` 沿光方向按高度扫掠 `Steps=7` 步，每步画一个底面矩形并取并集（每步 `Blend` 一次，颜色固定 `#0a0a0e`），得到连续的软阴影体。阴影层最终合成在物体**之下**（`under.Composite(shadow,0,0)` 再 `under.Composite(col,0,0)`）。日间 `ShadowA = 0.30`，夜间 `0.20`，方向 `DX=0.36, DY=0.155`。

## 7. 侧壁瓦片为何逐层堆叠

侧壁（`cliff.*`）每个原型只渲染**1 个高度单位**，占用与地形瓦片相同的 `Footprint{1,1}`，画布范围是独立的 `CliffBounds = {MinX:-17, MinY:-1, MaxX:17, MaxY:26}`（比 `TileBounds` 向下多 9 像素），面向 `e/s/w/n` 四个方向各一套，共 5 材质 × 4 方向 × 2 变体 = 40 张。

运行时不画「一整根高墙」，而是按落差层数**逐层堆叠**同一张瓦片：

```js
for (let k = 0; k < z - nh; k++) {
  const cn = this.pickVariant(`${prefix}.${SIDES[s].key}`, x + k*3, y - k, 2);
  // 在 project(x, y, z - k) 处贴一张
}
```

**为什么不能整列一次渲染。** 等距场景用的是画家算法（按 `d = x+y` 升序逐格绘制）。一块抬高的地块，其侧壁会与**更靠南（d 更大）的邻居地块**交错：邻居的地面、它自己的侧壁、以及更远处建筑的下半部分，都可能出现在同一列像素上。如果侧壁是一整张图，它在绘制顺序里只能出现在一个位置——要么盖住本该在前面的邻居地面，要么被后面才画的地形切掉。拆成 1 格高度的瓦片后，每层都跟着**自己所属的那一格**在这格被访问时绘制，遮挡关系自然正确。

同样的理由让地形瓦片统一使用 `NoTrim = true`（保持统一尺寸与锚点），否则裁剪会让不同内容的瓦片锚点漂移，拼接必然出现错位。

## 8. 图集装箱与锚点

`internal/sheet.Packer` 是**批量货架式装箱器**，它做两件对内存很关键的事：

1. **收集完所有图之后再按高度降序摆放**。货架装箱对顺序极其敏感——高度接近的图排在一起，
   右侧参差浪费会小很多。按加入顺序摆时利用率只有约 56%，排序后到 88~91%。
2. **每张图集按实际用到的高度分配**，而不是一律开一张 `W x maxH` 的大图。
   提高像素密度时图集面积按平方增长，这一步能省下三到四成。

单张图集高度上限压在 **4096**：再高就可能越过 GPU 纹理尺寸上限，令浏览器退回软件合成。
宁可多开一张图集，也不要把单张撑过 4096。

实测（326 个条目，含夜间共 652 张图）：

| 密度 | 图集 | 像素 | RGBA | PNG | 利用率 |
| --- | --- | --- | --- | --- | --- |
| 1x | 1 张 | 2.4M | 9 MB | 0.9 MB | 86% |
| 2x | 1 张 | 9.5M | 36 MB | 2.1 MB | 88% |
| 3x | 2 张 | 20.8M | 79 MB | 3.8 MB | 91% |

每个精灵图四周留 1 像素间隔（`Pad = 1`）——纹理过滤与图集上传不需要，但人工核对接触印相图时很有用。
运行时按 manifest 的 `sheet` 索引取图，支持多张图集。

`manifest.json` 中每张精灵图记录：

| 字段 | 含义 |
| --- | --- |
| `name` / `label` / `kind` / `category` | 名称、中文显示名、种类（`terrain`/`road`/`building`/`prop`）、UI 分类 |
| `variant` / `variants` / `anim` | 变体序号、原型总数、是否为动画帧而非随机变体 |
| `sheet` / `x` / `y` / `w` / `h` | 日间档的图集序号、左上角坐标、尺寸 |
| `ax` / `ay` | **锚点**：局部原点在图像中的像素位置 |
| `nightSheet` / `nightX` / `nightY` | 夜间档的图集坐标（`-no-night` 时为 `-1`） |
| `fp` / `h3d` / `cost` / `pop` / `jobs` / `level` | 占地格数、世界高度、造价、人口、岗位、成长等级 |

运行时贴图只需要 `anchor`——`screen = tileScreenPos - anchor`，任何偏移修正都不需要。这是整套管线里最重要的一个约定：**锚点把「建模时的局部坐标」与「运行时按格定位」解耦**，建模代码可以任意在局部坐标里摆放几何体。

## 9. 昼夜两档如何保证尺寸 / 锚点完全一致

夜间档不是「事后调色」，而是**同一网格在第二套 lighting profile 下重渲一遍**（`Night`：`ShadeScale 0.58`、`Tint #3b4059` 强度 `0.34`、窗户/招牌替换为自发光材质、`GlowGain 1.0`）。问题在于：日间与夜间的裁剪结果可能差一个像素，一旦尺寸或锚点不同，运行时替换贴图就会整体错位。

解决办法是夜间档**复用日间裁剪后的画布**：

```go
nb := render.Rect{
    MinX: -sp.AnchorX, MinY: -sp.AnchorY,
    MaxX: -sp.AnchorX + sp.W, MaxY: -sp.AnchorY + sp.H,
}
nopts.Bounds = &nb   // 手动指定 1x 画布范围
nopts.NoTrim = true  // 不裁剪
nsp, err := night.Render(name, mesh, nopts)
```

`Bounds` 用日间的锚点反推回「局部坐标下的画布范围」，再关掉裁剪，于是夜间图的尺寸与锚点在数学上必然等于日间图。管线仍然逐张断言：

```go
if nsp.W != sp.W || nsp.H != sp.H || nsp.AnchorX != sp.AnchorX || nsp.AnchorY != sp.AnchorY {
    fail(...) // 昼/夜精灵不一致
}
```

这条断言是防回归的保险丝：一旦有人改动 `Pad`、`Expand`、辉光半径或阴影参数，只要两边产生分歧就会在渲染阶段直接失败，而不是等到浏览器里看到偏移。

## 10. 参考场景合成器（可执行规格）

`cmd/prerender/scene.go` 的 `RenderScene` 是 Go 端的场景合成器，它与网页运行时使用**完全相同**的绘制顺序与锚点算法：

```
1. 按 d = x + y 升序逐格绘制地形、侧壁、道路；
2. 单体按「占地东南角」的 d 值排序插入绘制，
   即 key = (o.X + o.FW - 1) + (o.Y + o.FH - 1)，
   这样多格单体的精灵总是覆盖其占地内所有格子的地形。
```

对照 `web/js/render.js` 的 `build()`：它把单体按同一个 key 分桶（`byKey`），在每个 `d` 的地形循环结束后插入该桶的单体，然后 `object()` 用同样的 `project + anchor` 贴图。两边是同一套规则的两种实现。

因此这个合成器有三个身份：

1. **美术审阅工具**：`make scene` 输出 `build/scene.png`（2x 放大，只渲白天档），不需要浏览器就能看整体观感；`DemoScene` 构造一座 19x17 的小城（湖与沙滩、两级台地、农田、道路网、广场、市中心、湖滨住宅、工业区、绿化）。
2. **行为规格**：运行时如果想改绘制顺序，必须同步改这里；两者不一致就是 bug。
3. **回归基准**：`-only` 与 `-sheet` 让单张精灵图的变化可以脱离浏览器定位。

`sheet.Contact` 则输出接触印相图（默认 10 列、2x 放大、棋盘底、每格 8 像素边距），配合 `build/contact.png.txt` 的名称索引逐张核对美术质量。
