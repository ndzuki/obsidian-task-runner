# Agent Town × 等距预渲染：可行性评估与重设计（提案）

> 状态：**方案 A 已确认**（2026-09），并追加四条美术要求（见 §8）。
> 本文不改 `docs/agent-town-design-spec.md`（那是当前 SSOT）；它是「等距重做」的实施规格。
> 生成器在 `tools/isocity98/`（Go 离线管线，含那个复古等距城市沙盒本身），本页所有数字都是实测值。

---

## 0. 结论

**技术上成立，而且能让终端 TUI 版的移植成本大幅下降**；但要改三处架构假设，
其中两处是「必须改」，一处是「建议改」。同时必须认清：这是一次**风格换代**
（俯视 RPG 小镇 → 等距预渲染小镇），不是把同一张画换一种渲染方式。

| 维度 | 判断 |
|---|---|
| 美术上限 | **明显提升**。预渲染 + 有限色板 + 有序抖动 + 描边，得到 SimCity/PC-98 那种「精致且统一」的质感 |
| Rust 侧移植成本 | **大幅下降**。从「移植 2300 行程序化绘制算法」变成「解一张 PNG → 贴精灵图」 |
| 内存（TUI 硬指标 <20MB） | **可行**。1x 下帧缓冲 2.07MB + 图集个位数 MB |
| 与现有 spec 的冲突 | **3 处**：零外部资源 / 实时太阳角度 / 俯视→等距 |
| 运行时改动 | 面板的**数据与交互契约零改动**（`/agents`、`STAGE`、点击详情、roster、加油/定位/问答全部保留） |
| 新增的长期负担 | 多了一条**离线资产链**（Go 生成器 + 图集产物），改美术要重跑 |

**推荐**：分两阶段。一期只换「静态小镇 + 现有数据驱动」（风险最低、立刻能看到效果）；
二期再补连续光向与剖面模式。

## 1. 三个硬冲突（必须先决策）

| # | 冲突 | 现状约束 | 新模型的现实 | 严重度 |
|---|---|---|---|---|
| 1 | **零外部资源** ↔ 图集 | spec §10：`零外部资源（无图片/字体/库）`、单文件 HTML | 离线烘焙出 PNG 图集 + manifest | 必须解决（有干净解法） |
| 2 | **实时太阳角度** ↔ 烘焙光照 | spec §4：太阳方位连续变化、影子长度=高度角反比、方向反向 | 光影是**烘死**在精灵图里的（固定光向 + 昼夜两档） | 必须解决（需接受一处近似） |
| 3 | **俯视 RPG** ↔ 等距 | spec §1：`参考经典俯视 RPG 小镇画风` | 等距是另一套视觉语言，且**会遮挡** | 建议做，但要配缓解手段 |

### 1.1 冲突一：零外部资源 ↔ 图集

「零外部资源」的真正目的是**免构建、单文件、可移植**，不是「像素必须现算」。这个目的可以保留：

| 交付形态 | 做法 | 结果 |
|---|---|---|
| Web 面板（`GET /monitor`） | 图集 base64 内联进同一个 HTML | 仍是单文件、仍无外部请求；代价是 HTML 从 109KB 涨到约 1.5–4MB |
| Rust TUI | `include_bytes!` 进二进制 | **比现在更彻底**：单个自包含可执行文件，运行时零文件依赖 |

生成器是仓库内的 Go 代码（`make agenttown`），产物随仓库走。需要接受的代价：
改美术要重跑生成器；贡献者需要 Go 工具链。

> 另一条路是**在浏览器里跑一遍生成器**（把 Go 光栅化器移植成 JS，加载时烘一遍），
> 保持零产物。不推荐：等于维护两套光栅化器，且每次开面板都要多花几百毫秒。

### 1.2 冲突二：实时太阳角度 ↔ 烘焙光照（最硬的一条）

全连续光影 + 烘焙 = 资产爆炸：4 季 × 8 个光向 × 2 个昼夜档 = 64 倍图集，任何预算都吃不下。

**解法：把「形体」与「光」解耦，三者各走各的。**

| 要素 | 谁来算 | 说明 |
|---|---|---|
| 几何 + 材质三色调 | **离线烘焙**（一套） | 固定正午光向，保留描边与抖动网点 |
| **阴影**（长度/方向） | **运行时解析计算** | 每个建筑只需「占地矩形 + 高度」两个数；影子 = 占地沿光向扫掠出的六边形，用 50% 有序抖动填充。太阳角度**连续可变** |
| **色温**（季节/时段） | **运行时刻调色板重映射** | 4 季 × 4 时段 = 16 档外观，只对应 1 套资产（见 §4.4 实测） |
| 夜间窗户自发光 | 离线烘焙（第二档） | 这套管线本来就有 day/night 两档，直接复用 |

**明确接受的近似**：墙面朝向的明暗不随太阳移动（黄昏时左墙不会变暗）。
理由：**阴影才是「太阳在哪」最强的感知线索**，而它保留了。真要连续面光，就得烘 4–8 个光向变体
（1x 下图集 1MB → 4–8MB，仍在预算内），可以作为二期选项。

### 1.3 冲突三：俯视 → 等距（遮挡）

这是**一次风格换代**，spec §1 的风格总锚要从「俯视 RPG 小镇」改成「等距预渲染小镇」。
等距更精致、更有纵深，但对**监控**面板有一项实质代价：**建筑会挡住它后面的人和建筑**。

必须同时做四件事缓解（缺一不可）：

1. **压低体量**：占地 ≤2×2、高度 1.5–4 z，只有优先级塔/审计塔/钟楼到 6（已写进建模约束）；
2. **剖面模式**：再烘一套「去屋顶」变体（21 个建筑各 1 个，成本极低），一键看内部；
3. **遮挡透视**：居民被建筑遮住时叠加一层高亮轮廓；
4. **roster 仍是权威**：小镇负责「一眼看全局的氛围」，精确读数仍由 chips/详情面板承担。

另一个必须知道的几何差异：**等距的四个方向是菱形的四个「角」，不是四个象限**（见 §4.2）。

## 2. 实测：资产预算

生成器（`tools/isocity98`，`make agenttown`）把**现代城镇布局 + 21 个现代职业建筑 + 5 个道具
+ **21 个职业居民 + 12 个小精灵 + 4 个动物 + 四季形状资产**跑了完整管线，**含昼夜两档**（共 1770 张图）：

| 密度 | 内部画布 | 图集 | 像素 | RGBA | PNG | 离线耗时 | 利用率 |
|---|---|---|---|---|---|---|---|
| **1x** | 960×540（30x30） | 1 张 | 2.3M | **9 MB** | **1.22 MB** | 3.9 s | 86% |
| 2x | 1920×1080 | 1 张 | 9.0M | **35 MB** | ~3 MB | 13 s | 89% |

> 含 21 个职业建筑 + 10 种空隙填充、564 帧角色、四季形状资产、昼夜两档。

> 2x 的 PNG 体积按同比例估算；1x 为实测。3x 未做 —— 见下方 TUI 预算，它在 2x 就已超标。

参照系：城市沙盒那套 **42 个建筑原型 + 24 个道具 + 48 张道路瓦片 + 10 种地表**，
3x 下是 20.8M 像素 / 79MB。Agent Town 只用到其中的通用地面/道路/树 + 21 个建筑，
规模小一个量级。

**结论一：内联进单文件 HTML 完全可行。** 1x 图集 910KB → base64 约 1.2MB，
`agent-monitor.html` 从 109KB 涨到约 1.3MB。即便把 21 个职业居民、12 个小精灵、
4 个动物（共 564 帧）与四季形状全部算进来，也**只是 1.3MB 的单文件**，
「单文件 + 零外部请求」的不变量实际上只需要付出一倍多的文件体积。

**结论二：TUI 的 <20MB 硬指标只有 1x 能满足。**

| 密度 | 帧缓冲 | 图集 | 合计 | 对照 TUI 的 <20MB RSS |
|---|---|---|---|---|
| 1x | 960×540×4 = 2.07MB | 9 MB | **11.1 MB** | ✅ 达标（余量约 9MB） |
| 2x | 1920×1080×4 = 8.3MB | 35 MB | 43.3 MB | ❌ 超标 |

TUI 侧的目标「运行 RSS <20MB」在 1x 下**满足**。
（中途误解为放大分辨率时曾涨到 24.3MB 超标，回退画布 + 裁剪填充集后已恢复。）

## 4. 重设计方案

### 4.1 画布与视角

- 逻辑画布 **960×540 不变**（spec 已锁定）。
- 取 `SCALE=1`：1 格 = 32×16 px。**30×30 格的小镇正好 (30+30)×16 = 960 宽、(30+30)×8 = 480 高**，
  南北角各留 30px 余量放高层剪影 —— 尺寸是完全吻合的，不需要裁切或缩放。
- 高清屏可选 `SCALE=2`（内部 1920×1080）；TUI 用 1x。

### 4.2 布局：四象限 → 四角

spec §5 用**屏幕像素坐标**描述「横主街 y≈248..280 / 纵主街 x≈456..504 / 中央广场 x≈396..564,y≈184..356」。
这些数字在等距下**必须重新推导**，因为菱形地图的空间逻辑不同：

| spec 的方位 | 等距下的位置 | 内容 |
|---|---|---|
| 北 | 菱形**上角**（x+y 小） | 文职区 |
| 东 | 菱形**右角**（x−y 大） | 工业 / 开发区 |
| 南 | 菱形**下角**（x+y 大） | 自然区（池塘/农田/花坛/树林） |
| 西 | 菱形**左角**（x−y 小） | 知识 / 审计区 |
| 中央 | 菱形正中 | 中央广场 + 两条主街十字交叉 |

这其实**比原方案更自然**：小镇的中心就是广场，两条主街沿菱形的两个轴向穿过，
四个职业区各据一角。探针已按此实现（`cmd/prerender/agenttown.go`）：

- 四周入水（水岸小镇，spec 要求「水岸」），陆地抬高 1 格 → 自然的岸边崖壁；
- 两条 2 格宽主街在正中十字交叉；
- 中央广场 8×8 铺装，喷泉 + 旗杆；
- 四角各一条支路串起职业建筑；
- 沿街行道树 + 空地树林。

### 4.3 建筑 ↔ stage 映射

spec §6 的 21 个 stage 一对一映射成 21 个等距建筑（名字 `at.<stage>`）：

| 区域 | 建筑 |
|---|---|
| 北 · 文职 | `at.refining` 需求精炼坊、`at.planning` 规划院、`at.plan-review` 评审厅、`at.design` 设计工坊、`at.conventions` 规范文书房、`at.priority` 优先级塔 |
| 东 · 工业/开发 | `at.implementing` 开发工厂、`at.review` 验收场、`at.merge` 合并发布站、`at.conflict` 仲裁庭 |
| 南 · 自然 | `at.idle` 休息草坪(凉亭)、`at.pond` 池塘、`at.farm` 农田、`at.flowerbed` 花坛 |
| 西 · 知识/审计 | `at.audit` 审计塔、`at.knowledge` 知识树馆、`at.closed` 归档小馆、`at.split` 拆分工作台 |
| 中央广场 | `at.pm` 统筹议事厅、`at.working` 综合工位、`at.ready` 待命驿站、`at.blocked` 阻塞等待亭、`at.done` 凯旋广场、`at.needs-grilling` 访谈茶馆 |

**辨识度靠屋顶形状与招牌色**，不靠细节堆砌：21 个建筑各自有可区分的屋顶剪影
（双坡/四坡/平顶女儿墙/锯齿/圆穹/尖塔）与招牌色，1x 下也能一眼分辨。
`STAGE[key].color` 原本就是每个 stage 的标识色，直接用于招牌面板。

### 4.4 光与季节的解耦（核心设计，已实测）

**一套烘焙资产 → 16 种季节/时段外观**，代价是换档时扫一遍色板查表。

探针实测（`build/at_tint.png`，4 季 × 4 时段）：

- 季节规则示例：春 = 草 +1 档 + 树混入樱粉；秋 = 树混入 `c75447` 橙红 + 草混入土黄；
  冬 = 草/树/屋顶去饱和偏冷 + 天空提亮
- 时段规则示例：清晨 = 石材混暖黄；黄昏 = 石材/灰墙混砖红 + 天空橙红；夜晚 = 各色阶 −1~−2 档 + 混冷蓝
- 实现：97 色母板 → 一张 `uint8[97]` 重映射表 → 逐像素查表（1MB 图集 ≈ 26 万像素，可忽略）

**边界（要如实知道）**：重映射只改**颜色**，不改**形体**。所以：
- 常青树入冬不会变成光秃树（形状不变）
- 屋顶积雪需要额外的**覆盖层**：给地面瓦片和屋顶做一张「雪」抖动遮罩（离线烘 1 张，运行时叠加）
- 雪花/落叶/雨是粒子，属于运行时，与本方案无关

### 4.5 居民（agent）与装饰 NPC

| 项 | 预算 | 说明 |
|---|---|---|
| 真实 agent 居民 | 21 职业 × 4 向 × 4 帧 ≈ 336 帧 | 1x 下单帧约 16×24px → 合计约 13 万像素，可忽略 |
| 更省的替代 | 1 个基础身体 × 4 向 × 4 帧 + 21 个职业配件（帽子/工具）× 4 向 ≈ 100 帧 | 与现面板「调色板换装」的思路一致 |
| 装饰 NPC（16–20） | 路人/小孩/精灵/鸟/猫，各 4 向 × 4 帧 | 同上量级 |
| 配色 | 运行时色板重映射 | 现面板已经在做「随机 palette/帽子/围巾/发色」，可保留 |

**移动与碰撞完全不变**：A* 走 12px 碰撞网格、8px 双向分离力、聚集兜底 —— 这些是逻辑，
与渲染无关，零改动。只是「贴一个 sprite」替代「按行画像素」。

### 4.6 状态语义（监控可用性是第一位的）

等距版要让**状态一眼可读**，建议：

- 建筑本体：有人上班时**窗户亮**（夜间档自发光），人数越多亮得越多；
- `blocked` → 建筑上方红色闪烁标记 + 居民头顶 ⛔ 气泡；
- `needs-grilling` → 黄色 `?` 气泡；
- `done` → 凯旋广场放礼花粒子；
- 顶部状态条与 roster 逻辑不变。

### 4.7 数据与交互契约（**零改动**）

`GET /agents` 每 2s 轮询、`x-agents-finished` 计数、`GET /kb-stats` 每 30s、
`POST /agent/chat` 问答、点击详情/加油/定位、roster chips、空态文案 —— **全部保留**。
本方案只替换「画布怎么画」，不碰数据层与交互层。这也让它可以增量上线：
新旧渲染器可以并存，用一个开关切换。

### 4.8 资产链与两种交付形态

```
internal/catalog/agenttown.go      21 个职业建筑 + 城镇道具（Go 代码建模）
        │  make agenttown
        ▼
cmd/prerender -set agenttown  ──►  atlas_0.png + atlas_1.png + manifest.json
        │
        ├─ Web：base64 内联进 agent-monitor.html（单文件不破）
        └─ TUI：include_bytes! 进 Rust 二进制（比现在更彻底的自包含）
```

### 4.9 对终端 TUI 的影响

TUI 版当前的做法是「移植 `agent-monitor.html` 的 Canvas 绘制算法（…Uint32Array 逐像素缓冲…）到 Rust 侧」。
换成预渲染后，这一条**大幅简化**：

- 不需要移植 2300 行绘制算法（建筑形状、屋顶、树、水面全部变成了贴图）；
- 需要的是：PNG 解码（`image` crate）+ 精灵图 blit + A* + 同一套状态机；
- 内存预算更容易达标（见 §2）；
- 代价：Rust 侧要解析 manifest（很简单），并且**图集必须随二进制走**（`include_bytes!`）。

## 5.5 与现状的实测对照（重要）

把 `docs/assets/agent-town.gif` 与探针渲染结果并排看，评估结论会有一处重要修正。

| 维度 | 现状（俯视 RPG） | 探针（等距预渲染） |
|---|---|---|
| 观感 | 明亮、治愈、可读性强；建筑是「带立面的屋顶矩形」，抽象但清楚 | 更精致、有体积感与纵深；屋顶/侧墙/阴影齐全，像 SimCity/PC-98 |
| **遮挡** | **完全没有**——每个建筑、每个居民都完整可见 | **建筑会挡住后面的建筑与居民** |
| 标签 | 建筑名/居民名直接浮在头顶，位置天然正确 | 需要重新定位与分层（要画在建筑之上，否则被压住） |
| NPC 表现 | 俯视小人 + 气泡 | 等距小人（4 向 × 4 帧），更有立体感，但被挡住时完全看不见 |
| 风格身份 | 「RPG Maker demo 小镇」 | 「复古等距城市」——**是另一套身份** |
| 美术上限 | 受限于实时程序绘制的复杂度（每帧重画） | 高得多（离线烘焙，可堆细节、抖动、描边、发光） |

**修正后的判断**：等距不是单纯的美术升级，而是**用「一眼全见」换「立体精致」**。
对监控面板来说，「一眼全见」本来是核心价值 —— 所以 §1.3 那四条缓解不是「锦上添花」，
而是**方案成立的前提**；其中「剖面模式（去屋顶）」尤其关键，它其实把当前俯视视图
作为等距版的一个子模式保留了下来。

**因此我给出两个可选目标，而不是一个：**

| 方案 | 做法 | 适合 |
|---|---|---|
| **A. 等距重做**（本文主方案） | 换视角、换资产链 | 想要「作品级」观感，接受遮挡缓解的开发量 |
| **B. 只换画法、不换视角** | 保留俯视与全部交互逻辑，assets 仍由离线管线烘焙（俯视投影的精灵图 + 有限色板 + 抖动），运行时只贴图 | 想要美术质量与 Rust 移植成本的收益，但**不放弃监控可读性** |

方案 B 其实能拿到本文大部分收益（离线烘焙、有限色板、图集、Rust 侧变成 blit、
季节用调色板重映射），**且零遮挡风险**，代价是放弃等距的纵深观感。
如果目标优先级是「监控面板」而不是「作品」，B 的性价比更高。

## 8.1 要求一：布局要像现代城镇

**已重做。** 原探针是「RPG 村庄」式的十字主街 + 散落独栋，现在改为**现代城镇规划**：

| 维度 | 村庄式（旧） | 现代城镇（新） |
|---|---|---|
| 路网 | 一条横向 + 一条纵向主街，其余是自然小径 | **环形主干道 + 四条支路导入中央广场**（广场内不通车）；外圈还有一条水岸环带 |
| 街道断面 | 只在未连通方向长路缘石，读起来是乡间小路 | **新增 `road.street` 瓦片**：两侧人行道 + 路缘 + 中央虚线，2 格宽 |
| 建筑排布 | 散落的独栋，间距随机 | 按方正**街区**成组布置、统一退线，并**铺满全部 8 个街区 + 外圈水岸带**（见 §8.8） |
| 分区 | 四象限 | 北=市政文化 / 东=科技园区 / 南=公园水岸 / 西=办公核心 |
| 绿化 | 随机点缀 | **沿街等距行道树** + 水岸林荫步道 + 成片公园林 |
| 场地 | 草地为主 | 市政前广场、园区硬化地面、水岸铺装步道 |
| 中央 | 空地 | 8x8 铺装广场 + 现代水景 + 旗杆，四条支路在四角导入 |

布局是**手工规划**的（现代城镇的街区尺度需要人来定，公式生成只会得到均匀的格子），
并配了一条**自检**：建筑之间不得重叠、不得压路、脚下必须是平的陆地 ——
手写坐标写重了会直接报错，而不是变成画面里的怪事。

**已全部重做。** 21 个职业建筑从「乡村小屋 + 拟物趣味」改为**当代职场建筑**：

- **形态词汇**：平屋顶 + 女儿墙、屋顶设备（空调机组/水箱/楼梯间）、玻璃幕墙 + 水平楼层线、

- **体量**：占地 2x2 为主（最大 3x2），高度 3.5~10；两座地标（`at.priority` 地标塔 10.0、
  `at.audit` 总部塔 9.0）负责天际线，其余保持中低层以抑制遮挡
- 每个职业有**可辨识的现代建筑原型**，例如：`at.pm` 市政厅（玻璃中庭 + 前广场台阶）、

## 8.3 要求三：花草树木更自然 + 四季是否有状态与动态（**可以直接回答：能**）

先纠正一个我在 v1 里的**限制**：v1 的季节只是**调色板重映射**（只换颜色），
所以「入冬树变秃」做不到。要做到「季节状态」，必须把季节拆成**三层**，
分别用最便宜的手段实现：

| 层 | 内容 | 手段 | 成本 |
|---|---|---|---|
| **形状层** | 树秃了/开花了、水面结冰、积雪覆盖 | **离线按季节各烘一套**（只对形状真的会变的那几个原型） | 很小，见下 |
| **颜色层** | 草地/天空/墙面的冷暖与饱和度 | **运行时调色板重映射**（97 色 → 查表），零资产 | 0 |
| **动态层** | 落叶、花瓣、雪花、水波、树冠摇曳 | **运行时粒子 + 资产摇摆帧** | 很小 |

### 四季的具体状态（已实现并验证）

| 对象 | 春 | 夏 | 秋 | 冬 |
|---|---|---|---|---|
| 阔叶树 | 新绿树冠 + **花瓣点缀** | 茂密深绿 | 橙红稀疏 + 露枝干 | **没有树冠**：主干 + 秃枝 + 枝上积雪 |
| 针叶树 | 常绿 | 常绿 | 常绿 | 每层锥顶**压一层雪** |
| 灌木 | 嫩绿 | 深绿 | 黄褐 | **只剩枯枝** + 顶部积雪 |
| 花坛 | 盛花 | 盛花 | 残花 + 枯叶 | **整坛覆雪** |
| 水面 | 液态 | 液态 | 液态 | **结冰**（冰面材质） |
| 地面 | 调色板偏嫩绿 | 饱和 | 偏黄 | **积雪覆盖层**（`at.snow`，只在冬季存在） |

实现要点（`internal/catalog/season.go`）：

- `catalog.SetSeason("winter")` 让**季节成为与像素密度同级的管线参数**，建模代码里可以
  直接 `if isWinter()` 换形体；
- 只有**形状会变**的原型标 `Def.Seasonal = true`，渲染时按季节各烘一套，
  精灵名带季节（`at.tree.oak_winter_1`）—— **manifest 结构不需要为季节增加任何维度**，
  运行时按名字取图即可；
- 建筑与道路**不参与季节烘焙**（一套资产），它们的季节差异全部交给调色板重映射。

**动态表现**（第 3 条问的「动态表现」）：

- **树冠摇曳**：季节资产自带 3 帧摇摆（树冠水平微移 1~2 像素），运行时循环播放即可读出「风」；
- **落叶/花瓣/雪花**：运行时粒子，与资产无关（现有面板本来就有粒子系统，保留并换素材）；
- **雪落地面积累 / 冰面反光**：冬季铺 `at.snow` 覆盖层 + 冰面材质；
- 做不到的（如实说明）：草叶逐根摆动、树被风吹弯 —— 静态精灵做不了，
  只能靠粒子与整体调色板暗示。**不做**，投入产出比太低。

### 成本实测（1x）

季节烘焙只增加「形状会变」的那几十个原型 × 4 季（树/灌木/花坛/水面/积雪）。
1x 下实测：**不含四季时 885 张 / 4MB，含四季与全部角色后 1770 张 / 7MB** —— 只多 3MB，
**仍在 TUI 的 <20MB 预算内**（详见 §2 表）。

> 注意：1770 张已包含 **21 个职业居民 + 12 个小精灵 + 4 个动物（共 564 帧）**、
> 四季形状资产、昼夜两档 —— 即「一个完整可用的现代城镇面板」的全部美术。

## 8.4 要求四：NPC 与小精灵重新设计（v2 → v3）

第一版角色被否，原因是**「个性化」当时只是一个形容词，没有进入 CI**：
21 个职业只做了 9 个居民、配件只有 1~2 像素、3 个小精灵是同形换色、脸在 1x 下等于没有。

### 把它变成可量的门禁

新增两条测试（`internal/catalog/agenttown_test.go`）：

| 门禁 | 判据 |
|---|---|
| `TestAgentTownCharactersAreDistinct` | 角色总数 ≥34；且**任意两个角色**在 1x 待机帧上（以脚底锚点对齐、30x36 窗口）**差异 ≥10 像素**。测试会打印最相似的 12 对，直接当调优指南用 |

  `npc.implementer` / `npc.reviewer` / `npc.releaser` / `npc.auditor` / `npc.pm` /
  `npc.designer` / `npc.splitter` / `npc.blocked` / `npc.griller` / `npc.celebrant` /
  `npc.archivist` / `npc.standby` / `npc.resting` / `npc.worker` / `npc.legislator` /
  `npc.librarian` / `npc.prioritizer` / `npc.arbiter`），各 16 帧

  权衡天平 / 记录羽毛笔 / 抉择骰子 / 等待沙漏 / 庆祝星火 / 沟通云朵 / 拆分拼图 /

## 8.5 顺带修掉的既有 bug：四向旋转把模型甩出一整格

做角色差异化时量到一个反常数据：`npc.planner` 的锚点 `anchorX=22` 而精灵图只有 11 宽 ——
角色整个落在锚点左侧。追下去发现根因：

**`geom.RotateZ90` 绕的是原点 (0,0)，而车辆与角色都建在格子中心 (0.5,0.5)。**
于是「同一辆车/同一个人」的四个朝向分别落在**相邻格子**里：

| `car.red` 变体 | 修复前锚点 | 修复后锚点 |
|---|---|---|
| 0 | (10, 0) | (10, 0) |
| 1 | (26, 8) | (10, 0) |
| 2 | (10, 16) | (10, 0) |
| 3 | (10, 8) | (10, 0) |

漂移 16 像素 = **整整一格**。这不只是新角色的问题：**游戏里放置的车辆一直会显示在相邻格**，
只是车辆是静态道具、朝向由随机变体决定，所以看起来像「摆放位置有点飘」，很难定位。

修复：`RotateZ90` 改为绕格子中心旋转，并新增不变量测试
`TestRotateZ90KeepsModelOnItsTile`（离格子中心的距离守恒、不越出本格、转四次回到原位）。

## 8.6 遮挡缓解（已实现）

等距视角下建筑挡住后面的人，是方案 A 唯一的结构性代价。两条都已落地：

### 8.6.1 剖面模式：`at.<stage>.open`

同一栋楼多一个「剖开」的形态，一键切换就能看进内部 —— 本质上是把原面板的俯视视图
作为等距版的一个子模式保留下来。**不需要碰 21 个建筑的任何一行建模代码**：剖切是网格层面的后处理。

两个踩过的坑（都由门禁抓到）：

1. **按材质删屋面等于没切**。第一版按 `roof.*` 材质删面，实测只削掉 5~20 个面、
   高度几乎不变 —— 因为现代建筑的墙是一路砌到屋顶的，删掉最顶上那层薄片，
   你看到的仍然是墙顶。改成**真正的水平剖面**：在建筑高度 62% 处剖开，
   删掉剖面之上的一切。
2. **跨剖面的面必须夹断，不能只删**。`at.priority` 有从地面贯通到塔顶的竖向翼片，
   它是**一个**跨了几层高的面；只按「整个面在剖面之上才删」的规则它会被整片保留，
   剖完仍顶着 76% 高度（被 `TestAgentTownCutawayKeepsReadableMass` 抓到）。
   把跨剖面的顶点夹到剖切面，翼片才正确断开。

门禁：21 个剖面资产，保留高度必须落在 **45%~75%**（实测全部 ≈62%）。

### 8.6.2 遮挡透视（x-ray）

逐角色判断「胸口那一点」是否被**深度更大**的建筑精灵盖住，是则以青绿高亮剪影
画到最上层 —— 保持人形轮廓，一眼能看出「谁在楼后面」，而不是「那里有个点」。

两个关键实现细节：

- **必须逐像素采样对方的 alpha**，不能用矩形相交：建筑精灵的包围盒里有大量透明区，
  矩形判定会把站在楼边的人误判成被挡住；
- 查找遮挡物时**必须走变体名回退**（`at.pm` → `at.pm_0`）。第一版直接查原型名，
  永远 miss，于是透视数恒为 0 —— 这个 bug 是靠打印「0/28 个角色被遮挡」才发现的，
  画面上完全看不出来（效果就是「没有效果」）。

实测：**28 个角色里 9 个被建筑挡住并正确透出**。

## 8.7 1x 辨识度：量化复核（结论与直觉相反）

§5.6 列过一张「1x 下可能认不出」的清单，那都是建模 agent 自己上报的**主观担忧**。
把它们变成像素差之后，结论是**大部分担忧不成立**：

| 组合 | 实测差异 | 判定 |
|---|---|---|
| `at.audit` vs `at.priority`（两座退台塔） | **800 像素** | 远高于担忧，无需处理 |
| `at.closed` vs `at.split` | 811 像素 | 同上 |
| `at.refining` vs `at.conventions` | 1034 像素 | 同上 |
| `npc.refiner` vs `npc.librarian` | 200 像素 | 同上 |
| `npc.resting` vs `npc.griller` | 316 像素 | 同上 |
| `at.fountain` vs `at.pond` | **86 像素** | 唯一偏紧的一对 |

三条判据已固化为测试（`TestAgentTownConfusableBuildingsDiffer` /
`TestAgentTownConfusableCharactersDiffer`），阈值分两类：

- **真正的同屏易混对**（两座塔、两个方正低层）设高下限，要求明确拉开；
- **水景一对**实测 86：喷泉与池塘本来就该靠**位置**区分（喷泉在广场、池塘在公园），
  下限钉在 80 当**回归护栏**，防止哪天它们被改成同一套模型。

> 这一节的教训值得记下来：**「1x 下可能认不出」是主观判断，多数经不起量化**。
> 先测，再决定改不改 —— 否则会为了一个不存在的问题去改坏已经成立的造型。

## 8.8 布局放大与「人随岗位走」

**需求：城镇要更大、建筑与人要分散，不要挤一堆。** 做了三件事：

### 8.9.1 正解：不是分辨率，是**密度**

我先把「放大一倍」误解成了分辨率/地图尺寸放大（画布 1920x1080、地图 60x60、
161 栋填充建筑），用户随即澄清：**「不是指分辨率放大，是指布局挤在一起，
要更多街道空隙与活动空间」**。已回退，改为解决真正的诉求 —— **拉开间距**：

| 维度 | 上一版（挤） | 现在（拉开） |
|---|---|---|
| 画布 | 1920x1080（误改） | **960x540（回到 spec 原值）** |
| 地图 | 60x60 + 161 栋填充 | 30x30 + **16 栋**空隙填充 |
| 中央广场 | 6x6 | **10x10（占全图 11%）**，是小镇的主活动空间 |
| 建筑间距 | 肩并肩、1 格缝 | **彼此至少 2 格空隙** |
| 街区场地 | 铺满 | 广场四角另有 4 块 3x3 小活动场地 |
| 绿化 | 44 处 | 32 棵行道树 + 水岸林荫 |

做法上的关键一条：填充不再「见缝就插」，而是要求**离最近建筑 ≥1 格**才允许放
（`tooClose()` 预检）。**留白是设计的一部分，不是没排满** —— 这正是上一版挤成一团的根因：
我把「铺满」当成了目标。

顺带：回退画布也**修好了 TUI 的内存预算**（见 §2：放大版 24.3MB 超标，现在回到安全区）。

### 8.9.2 资产集服务于布局

上一版把城市沙盒**全部 42 个填充原型**都烘进了图集（8MB → 16MB），
而布局只用到 10 种。新增 `AgentTownFillerDefs()` 按需裁剪 —— 图集回到 9MB。
「把仓库里所有东西都烘一遍」不是资产集该有的行为。

### 8.9.3 居民站到自己的岗位楼前

21 个职业居民与 21 栋职业建筑**一一对应**，每人自动站到自己那栋楼的正面
（南侧人行道；被占则依次尝试东/西/北，再向外扩两圈）。实测 **21/21 全部到岗**。

这一步是「分散」在数据上的落地：**人不再聚在广场，而是随岗位铺开**。
运行时表现（接单后从休息点 A* 走到对应建筑、到岗播放职业动画）是面板侧的逻辑，
本布局提供的是**每栋楼的到岗位置**。

### 8.9.4 绿化/道具/角色一律走占位校验

手写坐标必然和建筑打架 —— 上一版实测撞了 **10 处**（绿化压在道路/建筑上），
全靠布局自检抓出来。现在建筑先摆完，再建占位集，之后所有绿化、道具、居民、
精灵、动物都先查 `free()` 再放，**放不下就跳过或退到备选位**，而不是叠上去。

顺带记录一条约束：人行道在数据上属于道路瓦片（`road.street` 自带两侧人行道），
所以「不在道路上」等价于「不在人行道上」——行道树只能落在街区路侧的空地。

## 8.10 四季 / 昼夜 / 天气强化

**需求：四季、昼夜与天气的变化要更强烈、特征更明显。** 三件事一起做了。

### 8.10.1 强度重新标定：目标是「一眼看出」

上一版的季节规则太保守（偏移 0~1 档、混色 12%~35%），实际观感是「好像有点不一样」。
新标准是**一眼看出是哪个季节/时段**，于是把强度整体提到：

| | 上一版 | 现在 |
|---|---|---|
| 色阶偏移 | 0 ~ ±1 | **0 ~ ±2** |
| 混色比例 | 0.12 ~ 0.72 | **0.20 ~ 0.85** |
| 覆盖色阶 | 2~4 条 | **4~8 条**（草/树叶/天空/屋顶/土/石/灰/水） |

四季现在是这样区分的：

- **春**：草 +1 档并混 35% 嫩绿，树冠混 55% 樱粉，天光转暖
- **夏**：草/树混 30% 深绿，天空混 32% 亮蓝，水混 22% 青蓝
- **秋**：树冠混 **85%** 橙红，草混 55% 稻草黄，天空混 28% 琥珀
- **冬**：草混 **80%** 雪白，屋顶混 55% 提白，天空混 40% 冰蓝，石/灰/水一并转冷

昼夜同理：清晨是**强暖橙**（石/灰/屋顶 35~42%、天空 60%），黄昏是**强砖红**
（天空 72%、石 45%），夜晚是**强冷蓝压暗**（各色阶 −2 档 + 50~58% 混 `2a3050`，
天空 82% 混 `141a2c`）—— 窗户自发光仍由烘焙的夜间档保留，夜里靠它撑住「有活人」。

### 8.10.2 全局色调：让**建筑与人物**一起换季

第二轮反馈：「四季的主题色调需要再突显，包括花草树木、**建筑、人物**」。

根因是我第一版的季节规则**只点名了草/树/天空/屋顶/土/石/灰/水**这几条色阶，
而建筑与人物用的是 `car.*` / `trim.*` / `wall.*` / `sign.*` 这些**没被点名的色阶** ——
所以换季时房子和人在画面里纹丝不动。

修法是把重映射分成**两层**，顺序不能颠倒：

1. **色阶规则**（点名某条色阶）：把草变黄、树变红 —— 定向改色；
2. **全局规则**（`ramp: "*"`，作用于整个色板）：叠一层季节色温 —— **建筑与人物靠它换季**。

全局规则必须作用在色阶规则**之后**，否则会把草/树的定向改色冲掉。

各季的全局色调强度（这是「一眼看出」的关键一笔）：

| 季节 | 全局色调 | 附加定向改色 |
|---|---|---|
| 春 | 20% 暖粉 `f0c8dc` | 树冠樱粉、砖/木偏暖 |
| 夏 | 16% 暖金 `ffe08a` | 草/树深绿、天空亮蓝、水青蓝 |
| 秋 | **32% 琥珀金 `e09a3a`** | 树冠 85% 橙红、砖 42%、木 45%、沙 42%、石 32% |
| 冬 | **34% 冷蓝白 `cfe0f0`** | 草 80% 雪白、砖 45%、木 40%、沙 50%、沥青提亮 35% |

### 8.10.3 天气与季节联动：气候而不是开关

采纳「天气跟着季节走」的建议。每个季节有**典型天气**，未显式指定时自动采用：

| 季节 | 典型天气 |
|---|---|
| 春 | **花信风**（樱瓣） |
| 夏 | **阵雨** |
| 秋 | **雾** |
| 冬 | **雪** |

`-weather` 留空即跟随季节；显式传 `-weather clear` 可覆盖（比如专门看冬天的晴天）。
四季对比图因此自动变成「春樱瓣 / 夏阵雨 / 秋雾 / 冬雪」——
一图同时展示季节与气候的对应关系。

### 8.10.4 天气：从「没有」到 5 种

原方案只有四季与昼夜，**天气是缺的**。新增 5 种，每种都是「色阶重映射 + 可见粒子」两件套：

| 天气 | 色彩 | 可见特征 |
|---|---|---|
| 晴 clear | 无 | — |
| 雨 rain | 天空混 55% 铅灰、整体去饱和压暗 | **斜向雨丝**（近大远小、越往下越长） |
| 雪 snow | 天空混 55% 灰白、屋顶/草/灰提亮 | **两档雪花**（大颗更亮，做出层次） |
| 雾 fog | 黑位抬 2 档、对比压平 | **横向雾带**，中上部更浓（远景糊掉、近景留清晰） |
| 花信风 petals | 天光与树冠偏粉、草提亮 | **粉白花瓣**带横向漂移轨迹 |

实现顺序有讲究：**先重映射（改全图色温）再画粒子** —— 粒子不该被重映射改色，
否则雪花会被染成天空色、雨丝会带上黄昏的橙色。

> 粒子在探针里是**静态合成**（固定种子，保证每次对比图一致），
> 运行时换成逐帧粒子即可，观感一致。

### 8.10.5 顺带修掉的 bug：空时段被当成夜晚

`timeRules(band)` 的分支是 `dawn / day / dusk / default→night`，
于是 **`band == ""` 落进 default，被当成夜晚**。后果：任何没传 `-tod` 的渲染
（比如 `make agenttown` 里的四季图）会整张压暗成夜景，而画面上完全看不出是配置错误
—— 只会觉得「怎么这么暗」。修法：`case "day", "": return nil`，并给四季分支补上 Time。

这类 bug 的共同点是**失败方向是「看起来不太对」而不是「报错」**，
所以现在三条对比图（四季 / 昼夜 / 天气）都是一条命令产出，改完就能并排看。

### 8.10.6 三张验收图

`make agenttown` 现在产出：

| 图 | 内容 |
|---|---|
| `at_seasons.png` | 四季 2x2（春/夏/秋/冬） |
| `at_tods.png` | 昼夜 2x2（清晨/白天/黄昏/夜晚） |
| `at_weather.png` | 天气 3x2 全尺寸（晴/雨/雪 · 雾/花信风） |

天气图用**全尺寸**而不是缩一半：雨丝/雪花/雾带全靠细节辨认，缩一半就看不出来了。

命令行也可单独指定：`-season autumn -tod dusk -weather rain`，任意组合。

## 8.11 落地：替换现有面板

用户确认后进入实施。分工是 **Go 侧当唯一事实源，JS 侧只负责贴图与动画**。

### 8.11.1 资产包与数据契约

`make agenttown` 现在多产出一个 `build/panel/`：

| 文件 | 体积 | 说明 |
|---|---|---|
| `atlas_0.png` | 1.22 MB | 精灵图集（单张 2048x1144，含昼夜两档） |
| `sprites.json` | 163 KB | **精简**精灵表（1880 项） |
| `town.json` | 29 KB | 布局 + 97 色调色板 + **80 张色板查表** |

内联成 base64 后 HTML 约 1.9MB —— 这是「单文件、零外部请求」的代价。

`town.json` 里最关键的一条设计：**80 张色板查表（4 季 x 4 时段 x 5 天气）由 Go 算好导出**，
JS 侧不做任何配色推导。理由是「秋天要怎么调色」这种事一旦在两边各写一遍，
迟早会漂移成两套观感；现在 JS 只负责「查表 + 换图 + 画粒子」。
查表是 97 字节的 Uint8Array（JSON 里是 base64 字符串，132 字符）。

为了缩小体积还做了两件事：地形名去重成 `terrainTable` + 下标数组（省掉 900 个字符串）；
精灵表只留渲染必需字段（完整 manifest 是 342KB，精简后 163KB）。

### 8.11.2 导出时抓到的坑：路网掩码没被导出

`scenMap.Road` 只存「这里有没有路」的标记，**真正的连通掩码是按邻格现算的**
（`roadMask()`），而导出器直接导出了原值 —— 于是 `road` 数组全是 `0`。
运行时会把每条路都画成孤立路桩（`road.street.0`），也就是**整条大道消失**。

这类 bug 的特征是「导出成功、格式合法、值全错」，光看导出日志发现不了。
修法是导出时逐格调用 `roadMask()`。修正后分布是 `-1: 836` + 64 格掩码
`3/6/7/9/11/12/13/14`（十字大道的直段、转角与丁字口），一眼就能看出对错。

### 8.11.3 面板已替换（实测）

`deploy/dsh-plugins/agent-monitor.html` 已重写为等距预渲染版：

| 体积 | 107 KB | **1.82 MB**（图集 base64 内联） |

### 8.11.4 面板开发中发现的 Go 侧 bug：参考图一直没有侧壁

运行时作者（子代理）在对照离线参考图与运行时画面时发现：
**`cliffName` 是基础名 `cliff.soil.e`，而精灵只有 `cliff.soil.e_0/_1`**，
两个离线合成器都用精确查找的 `set.Draw` —— 于是**参考图里根本没有侧壁**。

这个 bug 的隐蔽性在于：不报错、不留空洞，只是**少了立体感**。
岛屿边缘看上去仍有水岸与草地，很难察觉「崖壁那一层不见了」。
反倒是因为运行时正确走了 `_0` 回退、画面更立体，才把离线图的缺失暴露出来。

修法：两个合成器都改用带变体回退的 `drawV` / `set.DrawV`。

2. **遮挡**：塔类（10.0 / 9.0）会挡住后方。§1.3 的四条缓解仍需落地，
   其中「剖面模式（去屋顶变体）」建议进一期。
3. **季节与昼夜的组合**：现在是「4 季 × 4 时段 = 16 档调色板 + 4 套季节形状」，
   但要确认**夜间 + 冬季**的观感（雪地在夜里应该偏蓝，不能是灰白）。
